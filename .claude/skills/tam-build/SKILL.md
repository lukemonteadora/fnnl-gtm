# TAM Build (company-level, up front)

Build the client's whole addressable company and contact universe once, up front. First build a bounded sample, then the full universe after the GO gate. Once both TAMs are complete, `/lead-scoring` turns them into a ranked P1 through P5 queue. `/campaign-strategy` runs only after that score is complete.

The cost trick is two splits, not one. **(1) Company-level vs per-contact:** everything here is company-level (discovery + web crawl + company databases + Claude Code sub-agent normalization), which is flat/per-page cheap; the expensive per-contact layer (verified email, phone, verification) is deferred to the live slice in `/email-waterfall`. **(2) Qualify vs enrich, *within* the company layer:** discover the universe and capture the full source-native field set, score ICP fit (good/maybe/bad) cheaply from the discovery source's already-returned text plus any free homepage text it exposes (Claude Code sub-agents fanned out over disjoint batches do the classify; a web crawl only escalates the ambiguous rows, never every company), then collect the expensive beyond-source signals (org-depth, ads, multi-page proof/pricing/careers) **only on the companies that pass the fit gate** (Seat A enriches them hands-free via its own tools by default; the operator can instead finish them in an external enrichment round-trip). Qualify it cheap; pay to enrich only the good-fit slice, and pay for contacts only on the slice that goes live. (This qualify-then-enrich mechanic runs on a bounded **sample** in Phase A and on the **full universe** in Phase B, see the HARD RULE below, never blindly on "the whole TAM in one shot.")

## TAM-First Sequencing. HARD RULE (sample -> GO -> full + enrich -> THEN campaigns)

The whole point of building the TAM up front is that **campaigns are sliced from data points that actually exist in the list.** So the TAM must be fully built and enriched *before* any campaign idea is generated or any approval brief is written, never the other way around. Outputting campaign ideas without knowing the real, available data points of the actual lead list is the exact failure this rule prevents. This gate is binding and applies regardless of `execution_mode`.

**`run_state.status.tam_stage` is the single source of truth for where the TAM is** (this replaces the old `complete` value, which was ambiguous: `complete` previously meant only "a sample was built" and must no longer be used):

| `tam_stage` | Meaning | What may run next |
|---|---|---|
| `none` | not started | `/data-point-discovery`, then this skill (Phase A) |
| `sample_built` | a bounded **sample** is built + qualified; seed/ICP fit validated; this is **NOT the full universe** | hold at the GO gate below (auto-approves within ceiling under `auto_execute`, else stops); nothing downstream may run until `full_enriched` |
| `full_enriched` | the **whole qualified universe** is discovered, qualified, and enriched with the catalog's `collect_now` data points; company and contact TAMs are complete | `/lead-scoring`, then `/campaign-strategy` |

**Phase A: sample build and validate, then `tam_stage: sample_built`.** Build a **bounded** sample, attach cheap firmographics plus the Tier-1 cheap fit classify (the discovery source's returned text plus any free homepage text it exposes), score `fit_status`, and confirm two things: the fit-rate is sane (**tune the query to 80%+ sample fit before scaling**, measured on ICP fit, which is what the query actually controls, with the offer-fit drop rate reported separately per Gate reporting because no amount of query tuning fixes a market that cannot use the offer; per the discovery-source validation rubric: 80%+ means stop tuning and do not over-tweak a good query; 75-80 means minor tweaks; under 50 means rework from scratch) and the seed/ICP converges into ONE vertical rather than a contaminated list; and the priority `collect_now` data points are actually collectable for this vertical. A sample is ALWAYS bounded, never the full pull. What bounds it depends on the discovery spine:
> - **Lookalike / seed motion, the PROVEN motion and DEFAULT:** the natural first discover batch (a few hundred companies) is the sample. **Use it to tune the discovery source's similarity threshold (and its variance/breadth control) to the point where the sample's fit-rate is acceptable BEFORE the full pull.** A lookalike tool's similarity score is the precision lever, so a well-set threshold means the full-universe fit pass has less to remove and you re-pay the per-record credit for fewer off-ICP rows. **Check the tool's unset defaults before your first pull: lookalike tools commonly default to their most permissive setting, which is not what you want.** Seed from the group's case-study/customer companies (the 5-AI-plus-5-client seed rule, where the client seeds ARE the group's case-study companies from `/social-proof-bank`), and promote validated-`yes` companies to seeds as you tune.
> - **Filter motion, the EXPANSION motion (net-new segment / no-proof new offer only):** one query can return the *entire* universe at once, so there is no natural sample. Cap it explicitly. Pull only a bounded slice for Phase A (e.g. the first ~300 by the tool's own ranking, or a representative spread across the key firmographic bands and segments), validate on that, and leave the full pull for Phase B. Use the tool's free count/total endpoint to size the universe WITHOUT enriching it.
>
> Present the sample, its fit-rate, the projected **full-universe** size, and the projected full-TAM enrichment cost.

**GO gate (auto-approves within ceiling under `auto_execute`; otherwise a manual stop).** Scaling the sample to the full universe is BOTH a strategy decision ("whole universe now, or launch on a slice first?") AND a spend decision (full-universe enrichment is real money), so it stays a gate. But under `run_state.execution_mode = auto_execute` the operator has already chosen "proceed and pick the strongest option," and the strongest default under the high-volume doctrine IS the whole universe, so do not serialize the common case on a click. **Auto-approve Phase B (report it, do not stop) when ALL of these hold:** (1) the previewed full-universe enrichment cost is at or below the remaining `run_state.spend_ceiling_usd` (a real number greater than 0), (2) no slice-first / partial-build instruction is on record for this client, and (3) discovery converged on one vertical at the Phase A fit target. On auto-approval, report it like any within-ceiling spend ("GO gate auto-approved: full-universe enrich ~$X within $Y ceiling; N survivors") and continue to Phase B. **STOP for the operator's explicit "build the full TAM" when ANY of these hold:** the previewed cost exceeds the ceiling, `spend_ceiling_usd` is a 0 the operator set on purpose (a null, unset, or old-default 0 is first rewritten to the standing 100, per `/autonomous-execution-policy` section 2), the operator asked to launch on a slice first, or the mode is `review_gates`. This keeps the human stop where it earns its keep (a real spend fork or a deliberate slice-first launch) without pausing every hands-free run. The over-ceiling stop is the same one the Phase B Collection-completeness rule already enforces below, so the two never disagree. **Division of labor.** Seat A (this Claude Code) always does discovery (full source-native capture) and the ICP-fit decision (cheap classify by Claude Code sub-agents over the discovery source's already-returned text plus any free homepage text; a web crawl escalates only the ambiguous rows, then Claude judges good/maybe/bad). Beyond discovery and fit, **by default (`seat_a`) Seat A does ALL the enrichment hands-free: source-native first, then every beyond-source column via its own tools.** Claude pulls what the company-data provider returns (its company-search rows already carry the firmographics; where the provider exposes a bulk-domains mode, use it for a known-domain set) and what the company-discovery source's own native enrichers return, then collects the beyond-source columns (web crawl, paid-scraper ads, org-depth, web search) itself via the Layer 1b fast crawl. Record `run_state.tam_enrichment_path`: **`seat_a`** (default), where Seat A completes the entire `collect_now` set itself, source-native and beyond-source alike, with no external round-trip; **`seat_a_then_revcode`**, the operator's GO-gate choice to instead hand the beyond-source columns to the external enrichment platform named in the stack contract via the Layer 1c copy-paste handoff (a blocking round-trip they run with their own keys and integrations). This is the operator's call at the GO gate, not a forced default. Once the operator says go, discovery, fit and enrichment all run hands-free under `seat_a`; only the optional external leg blocks.

**Phase B: full TAM build and enrich, then `tam_stage: full_enriched`.** Discover the **full qualified universe**, qualify it cheap (Layer 1a, drop only `bad`), then complete the `collect_now` data points on every survivor:
- **Seat A: discover + validate fit (always).** Capture the full source-native field set, run the fit decision (cheap classify of the source's returned text plus free homepage text via Claude Code sub-agents; a web crawl only to escalate ambiguous rows), and apply the fit gate. Hands-free.
- **Enrich on `enriched` survivors.** Claude pulls the source-native columns (the company-data provider first, then the company-discovery source's native enrichers, Layer 1b). For every column needing a tool beyond those two, generate the copy-paste external handoff prompt (**Layer 1c** below), present it for the operator to run, then **BLOCK and wait for the returned enriched CSV** and join it onto `tam.csv` by `company_domain` (while blocked, do NOT scrape those columns yourself or proceed to campaigns).
- **Seat A: derive + write (always).** Derive the free columns and write `tam.csv`.

"Full qualified universe" means every ICP-fit survivor enriched (so you never hunt for more companies again), NOT every raw discovered domain. Keep the cheap-qualify-before-enrich gate below: discover broadly, drop `bad` fit cheaply, pay to enrich only survivors. Set `tam_stage: full_enriched` ONLY once the full survivor set is enriched (whichever path).

**Collection completeness on survivors. HARD RULE.** Enrich every good-fit survivor with **every obtainable** `collect_now` data point and signal the catalog carries: the whole obtainable set, not a ranked subset. The TAM is built once and is the asset every campaign slices from, so completeness here is what lets the operator launch many campaign slices per client off whatever signals each company has. Signal collection is a MUST, not optional. This applies to the **Phase B full enrich** (NOT the Phase A sample, which stays bounded so the GO gate still means something). The spend ceiling is the only limit, and it is operator-surfaced: if the previewed cost to collect the full obtainable set across survivors exceeds `run_state.spend_ceiling_usd`, STOP and surface it with a recommendation to **raise the ceiling to cover full collection**; trim by rank only on the operator's explicit say-so, never silently dropping obtainable signals. (Collect all up front; *launch* the resulting slices in sequenced waves per `/campaign-strategy`: collection and launch are different layers. `/data-point-discovery` Collection Completeness owns the principle.)

**The downstream gate (binding).** `/campaign-strategy` and `/campaign-approval-brief` MUST refuse to start unless `run_state.status.tam_stage == full_enriched` and `run_state.status.scoring_stage == complete`. A sample TAM or unscored TAM is not enough. Route incomplete TAM work back here and incomplete scoring to `/lead-scoring`.

## Case-Study-Anchored Discovery. HARD RULE (the discovery spine; operator directive 2026-07-03)

The company TAM is built **per group**, and the primary discovery spine is a **lookalike pull seeded from the client's own validated case-study / customer companies**: a MUST, not "operator's pick." **The company-data provider is the ENRICHMENT layer** (company detail plus contact discovery), never the discovery spine. (Bonus: this removes flaky-tool-first fragility, because an enrichment-connector outage now degrades enrichment gracefully instead of stalling discovery.) Two motions, and each group runs exactly one:

1. **PROVEN motion (DEFAULT): case-study-seeded lookalike.** For any group where the client has at least 1 real customer win: seed a lookalike from that group's case-study/customer company websites (from `/social-proof-bank`), promote validated-`yes` companies to seeds as you tune the similarity threshold, then enrich survivors with the company-data provider first. This is a lookalike tool's high-precision mode (~68% true-ICP vs ~39% for a raw category pull).
2. **EXPANSION / net-new motion: broad ICP filter.** For a segment the client wants to enter but has NOT sold to yet (no case study), OR a brand-new offer with no proof: build via a broad ICP filter (a filter-based company search, or a category / natural-language ICP query on the discovery source). A deliberate FIRST-CLASS motion (net-new / offer-validation), flagged `discovery_motion = expansion` so copy stays offer-led with no client-specific proof. Lookalike-from-wins is structurally blind to segments the client has never sold to, which is why this stays first-class: it is not a fallback.

**Grouping.** Case studies group by sub-industry / what the company sells or does (who they serve / same service). A group may hold 2+ case studies or just 1. **Each group gets its own seed set, its own group-TAM, and its own campaign(s)**; more groups means more TAMs and more campaigns. Record `group` and `discovery_motion` alongside `segment` on `tam.csv`.

**SEED vs PROOF (two gates, do not conflate).** The case-study *company* SEEDS the lookalike (it may be a case study, a happy customer, or a flagged aspirational exemplar). The case-study *facts* (exact number, timeframe, referenceable client) are the PROOF gate the copy will later need: at the point a group's case study is used as a seed, `/social-proof-bank` must confirm the group carries copy-ready proof-facts. If missing, flag the specific gap and collect from the client (`/proof-asset-request`) in parallel with the group's TAM build. **The seeds gate the lookalike build; missing proof-facts never hold it** (operator directive 2026-09-22): they gate only copy that names or quantifies the case study, and the group's offer-led copy ships without the proof line meanwhile. Expansion-motion groups have no proof gate (offer-led copy).

**Volume: the expansion-for-volume ladder (HIGH-VOLUME DEFAULT, operator directive 2026-07-07).** The lookalike stays the **precision spine**, but a group-TAM's natural saturation (~2,708 unique off one seed set) is **a trigger to WIDEN, not a ceiling.** The target is 1,000 to 20,000 leads per campaign, and most of that comes from **contacts-per-company** (Layer 1d pulls every ICP-matching buying-committee role, so a ~2,700-company lookalike feeds a 10k+ lead campaign without more companies). When a group-TAM still needs more *companies* to hit its campaign's volume, expand in this order, **re-checking ICP fit at every step (fit will drop as you widen, by design, so this is the calibrated gate below, NOT a re-clear of 80%):**
1. **More / stronger seeds:** seed from **5 or more** of the group's case-study/customer companies (a target, not a blocking floor; respect the discovery tool's seed cap and keep the AI-5/client-5 balance; fall back to a seed cascade if the client has fewer than 5), and promote validated-`yes` companies into the seed set.
2. **Loosen similarity:** lower the similarity threshold toward the tool's mid band and raise its variance/breadth control, paging under a server-side exclusion list so you bill only net-new.
3. **More markets / geographies:** add adjacent countries/regions the client can serve or sell into.
4. **Wider headcount bands:** add the adjacent employee-size buckets where the offer still lands.
5. **Merge sibling group-TAMs:** combine closely-related groups (same buyer, same message) into ONE big campaign.
6. **Broad ICP-filter expansion top-up (last):** deliberately add the EXPANSION motion, flagged `discovery_motion = expansion`, offer-led copy.

**The fit gate, anchored correctly ("when it makes sense only").** 80%+ is the TUNING target for the tight seeded core (tune it before scaling, unchanged); it is NOT the widening stop. Widening (rungs 3 to 5) deliberately reaches less-similar-but-still-relevant companies, so fit drops there by design, and that is allowed. Keep widening while the pull stays on-ICP down to the validation rubric's ~50% REWORK floor; flag companies pulled past the tight proven-fit core as `discovery_motion = expansion` (offer-led copy, no client-specific proof, per rung 6). **STOP when fit hits the ~50% rework floor (you are pulling noise) OR the campaign's volume target is reached, whichever comes first.** Never a blanket 80%, never merely a count. Requiring 80% on every widened rung would throttle the very company-expansion the 20k target needs. Volume pulled *below* the rework floor is bounce risk, not volume. The old "sum many small precise group-TAMs" idea survives as rung 5 (merge siblings into a big campaign), not as a ceiling. The full ladder and its capacity math belong with the high-volume doctrine this workspace records.

**Sequencing.** The group's SEED set (`/social-proof-bank`) must exist BEFORE this skill runs for that group (proof-facts are collected in parallel and never hold the build, operator directive 2026-09-22): it is what seeds the lookalike. See `/cold-email-kickoff`.

## The Cost Model (the "right order and way")

### Layer 1a: qualify up front (cheap, company-level)

> **Phase scope (per the HARD RULE):** in **Phase A** this qualify pass runs across the bounded **sample**; in **Phase B** it runs across the **full** discovered universe. "Across the whole thing, cheaply, before enriching" is the principle *within whichever phase you are in*. It is NOT a licence to discover and qualify the entire universe during Phase A (that would moot the sample-first GO gate).

Cost here is flat or per-page, not per-contact-credit, so qualifying every company in the current phase's set is affordable. This sub-layer ends at a **fit gate**; only survivors reach the expensive Layer 1b.

1. **Discover the company universe, primary spine per the Case-Study-Anchored Discovery HARD RULE above (a MUST, not a free operator pick).** **PROVEN motion (DEFAULT):** seed a lookalike from the group's case-study/customer company websites (from `/social-proof-bank`). **EXPANSION motion (net-new segment / brand-new offer with no proof):** a filter-based company search (filtering on company size, HQ location, industry, ownership status, last funding round, revenue band) or a category / natural-language ICP query. **The company-data provider is the ENRICHMENT layer (Layer 1b), never the discovery spine.** **Everything else is extension/augmentation, not the primary list:** WebSearch (SERP/URL discovery to *augment* coverage), maps/local scrapers (a truly local-SMB / maps-first universe is its own motion), and vertical revenue databases layer on top of the spine, never replace it. Discovery is the company list, not contacts. **HARD RULE (cost): every discover/count call carries the client's employee-size range, location and hard filters, and no lookalike is over-pulled.** Apply the client's `icp_hard_filters` from `client-profile.yaml` to the discovery query, never a hardcoded range: read `headcount_buckets_in` / `headcount_min/max`, `countries` / `states`, `industries_in/out`, and `revenue_min_usd`, and pass them as the discovery filters (on the lookalike too, not just filter-only queries) so you never pay to pull out-of-ICP rows. And never overpull a finite lookalike: count first (free), take one clean pull, and guard any follow-up pull with a server-side exclusion list so duplicates are never re-billed. **Filter caveat to verify on whichever tool fills the slot:** employee-size filters are frequently **bucket-based and include any OVERLAPPING bucket**, so a request for 100-2000 can return a whole 51-200 bucket (down to 51) AND a whole 1001-5000 bucket (up to 5,000). So (a) set the range to the client's exact `headcount_buckets_in`, and (b) **post-filter returned rows by their `headcount` bucket to the ICP set**, because a per-record-billed source still charges for any overlapping-bucket row it returns (choosing buckets deliberately is the real cost lever). Lookalike (domain-seed) mode normally applies the same firmographic filters at the same bucket granularity, not looser: verify this on the chosen tool rather than assuming it. A raw category pull is also noisy (category taxonomies routinely file vendors, SaaS and adjacent suppliers under the vertical, e.g. ~39% true-ICP on a broad vertical category), so the ICP-fit pass (steps 3-4), not the category filter, is what removes them. **Read the chosen discovery source's own capability map, model routing and plan gates before routing a discovery/research job there**, and confirm which filters its current plan actually unlocks: tech-stack/vendor filters, query inclusion/exclusion, AI segmentation and bulk name-matching are commonly gated to higher tiers. Never route a discovery filter through a tool whose plan does not expose it; get that signal another way.
2. **Capture the discovery tool's FULL native field set on every company (source-native full capture).** The discovery response already holds far more than a few firmographics, and everything in it is **free beyond the per-record search credit already spent**, so write EVERY field the tool returns to `tam.csv`, never a cherry-picked handful (the failure that produced a domain + name + score-only list). A company-search response typically returns, in one payload: identity (name, domain, LinkedIn, provider id), firmographics (company type, ownership status, company size, HQ location, industries, SIC/NAICS, revenue, funding round/amount/date, IPO/acquired dates), web-traffic (monthly visits, global/country/category rank, bounce rate, pages-per-visit, visit duration, top topics), sales-motion signals (pricing available, demo available, free trial available, documentation exists, downloadable, mobile apps exist, online reviews exist), tech (technologies used), and hiring (job posting title / seniority / type / location). A lookalike discover response typically returns domain, company name, industry, headcount, headcount range, location country / state / city, LinkedIn URL, description, and a similarity score. Map these onto the STABLE CORE canonical names and keep every remaining field as a **source-native extension column** (verbatim source name and value). Do NOT trim to a catalog subset: the catalog governs data points BEYOND the source response, not the source's own free payload. A company-search source is typically metered **per record returned**, so a whole-TAM pull is per-company spend. Estimate `records x per-record` via `/api-cost-governance` (the fields are free; the records are not).
3. **Free disqualifier pre-screen (firmographic AND offer-derived), then a cheap fit classification from data the discovery source ALREADY returned, not a fresh crawl.** First drop any company that fails a hard firmographic/discovery-snippet disqualifier; that costs nothing. Then drop the companies the offer itself rules out, also for nothing, and only then qualify what is left.

   **The offer-derived disqualifier list (free, and it runs BEFORE any paid classification).** Some companies are unsellable for a reason the ICP cannot see: they cannot use the thing this offer delivers. Screening them here, in the free pre-screen, is strictly cheaper than paying a classify credit and then an enrichment credit to discover the same thing later. **Build the list from the LOCKED offer set** (per segment, operator decision 2026-09-22: a company is auto-DQ'd only when every offer in its segment's set disqualifies it, the intersection of their `offer_fit_disqualifiers`) at the start of Layer 1a: read `offer.lead_magnet` plus its detail fields (`offer.lead_magnet_details`, `offer.lead_magnet_cta_direction`, `offer.lead_magnet_gap`) from `client-profile.yaml`, and the selected magnet's write-up in `lead-magnets.md`. **The list has one canonical home: `offer.offer_fit_disqualifiers` in `client-profile.yaml`, written by `/lead-magnet-brainstorm` at offer lock.** Read it from there. The three cases are distinct and must not be collapsed: a populated list is authoritative, so use it as written and do not re-derive alongside it (two lists silently drift, and the pre-screen would start dropping companies the offer work never sanctioned); an explicitly empty `offer_fit_disqualifiers: []` is a real answer meaning this offer excludes no company type, so the gate runs and drops nobody; the field being **absent** means offer lock never wrote it, so derive the list here and say so in the build report, because a silently self-derived list is the drift this join exists to prevent. Each entry answers one question, the same question the `offer_fit` judgement in step 4 asks: **can this business actually use, stock, deploy, or buy the thing the offer delivers?** The recurring categories, to be instantiated against this client's actual offer rather than copied verbatim:
   - **Already has its own version of this** (the canonical one). A private-label manufacturing offer excludes the clinics that already own a supplement brand: they are the offer's competitor, not its buyer.
   - **Franchise or head-office-controlled entities that cannot decide locally.** The local site cannot buy, and the entity that can is not the row you discovered.
   - **No physical or operational capability to use the deliverable.** No premises, no fleet, no lab, no team, no license: whatever the offer structurally requires.
   - **The client's existing customers.** Already sold; route them to the client, never to a cold campaign.

   **Matching discipline for an auto-DQ is NAME + DOMAIN only, exactly as strict as the `hard_no` rule below, and it is not to be loosened.** Keyword and specialty matching over-DQs real ICP accounts at a rate this repo has already measured (290 false positives versus 23 true name/domain hits, verified 2026-06-13). So an offer disqualifier auto-DQs only when it is decidable from the company's name and domain. **Anything that needs a judgement call is NOT an auto-DQ:** it drops through to the `offer_fit` classification in step 4, where the Tier-1 and Tier-2 machinery already exists to settle it. The free pre-screen takes the certain cases; the classify pass takes the rest. **What an offer auto-DQ must write:** `offer_fit = no` plus a one-line `offer_fit_reason` naming the disqualifier, and `fit_status: bad` with the matching `fit_reason`, then `enrichment_tier = qualified_out` (the same treatment `hard_no` gets below, and the row is never deleted). Skip those values and the survival ledger cannot count the row under `dropped_offer_fit`, so the reconciliation breaks on exactly the rows this pre-screen removed.

   **Then qualify every company that survived both pre-screens, in two tiers, cheapest-first.** **A lookalike source has already crawled these sites and returns their text, so re-running a web crawl plus a web search to re-derive "what does this company do" on every company is redundant work: removed.** The fit *gate* stays (it is what removes off-ICP rows and stops you paying per-record enrichment on them); only its *mechanism* changes:
   - **Tier 1: cheap classify on already-returned text, every surviving row, NO crawl.** Score fit from what discovery already paid for: the source's `description` plus industry/industry-group, business model and keyword fields (treat a similarity score as a relevance *prior*, NOT a fit verdict; verified ~68% true-ICP on lookalike and ~39% on category, which is exactly why a fit pass still runs), and for filter-sourced rows its returned fields, top topics and sales-motion booleans. Where the discovery source offers **free homepage text extraction for a domain just discovered this cycle**, pull it to deepen the context at no cost. **Claude Code sub-agents classify this in disjoint batches** (per `/personalization-subagent-pattern` and `/ai-model-routing`: each sub-agent reads its own slice of the on-disk text and writes its own output file, merged by `company_domain`). At sample scale a discovery tool's own native ICP-fit validator can be a convenient alternative, but those flood context past a few hundred rows, so the sub-agent fan-out is the full-TAM workhorse. **This same pass emits the `offer_fit` judgement (step 4), on the same text, for no extra credit.**
   - **Tier 2: escalate ONLY the ambiguous rows to a deeper crawl.** When Tier 1 returns low `fit_confidence`, a borderline `maybe`, or an `offer_fit = unclear` that deeper pages could resolve, THEN run a multi-page web crawl (pricing, `/customers`, `/about`), compress with a Claude Code sub-agent, and re-score. This bounds the crawl to the minority of companies whose fit is not decidable from the homepage plus returned text, instead of crawling everyone. **An `offer_fit` still `unclear` after escalation survives on the ICP verdict. It is never resolved to `no` by default**, because a default-to-drop ambiguity bucket is exactly how a launch slice starves.
   This is the `gate_role = qualify` work, now sourced from the discovery payload plus free homepage text first, with the crawl reserved for escalation. The `gate_role = enrich` data points come later, on survivors only (Layer 1b: Seat A via its own tools by default, or the external round-trip under `seat_a_then_revcode`).

> **Why classify, not re-crawl (and why the gate still exists).** A lookalike tool's automatic similarity score is *relevance-to-seeds*, not a good/bad ICP verdict: verified on a client TAM at ~68% true-ICP (best lookalike) and ~39% (category). So the fit **gate** stays, because it removes that off-ICP slice AND prevents per-record enrichment spend on it. But the external crawl that used to run on **every** company is removed, because the discovery source already crawled the site and hands back the text. Net: the costly per-page crawl drops to the ambiguous minority, the classify runs in Claude Code sub-agents with no per-row AI spend, and the list stays clean.
4. **Score fit (good / maybe / bad): TWO judgements on ONE pass, ICP fit AND offer fit. Claude's decision.** Run the fit filter (the `/icp-prompt-builder` prompt, tuned on a ~40-row mixed sample of THIS TAM's cheap layer: the source-native fields plus the free returned text/homepage from step 3's Tier 1, plus the escalation crawl on the ambiguous rows, to convergence) across the whole cheap TAM on a **parallel batch path, never a serial row-by-row loop in the main conversation** (the no-serial-independent-work default in `/autonomous-execution-policy` section 9). Claude Code Task sub-agents fanned out over disjoint slices are that parallel path, for the bulk and for edge cases alike (per `/personalization-subagent-pattern`: one output file per agent, merged by id, then a post-merge uniqueness check). Claude makes the good/maybe/bad call; write `fit_status` (`good`|`maybe`|`bad`), `fit_confidence` (0-1), and a one-sentence `fit_reason`. This is the "review good-fit / bad-fit" gate the note calls for, made cheap and automatic instead of a manual review of hundreds of rows.

   **The `offer_fit` judgement, evaluated against the LOCKED offer on the SAME classify pass (HARD survival gate).** ICP fit answers "is this the kind of company the client sells to." It does not answer the question that actually decides whether there is a sale here: **can this business actually use, stock, deploy, or buy the thing the offer delivers?** A company can sit dead centre of the ICP and still be unsellable this wave because the offer has nothing it can take. So the classify pass makes a second, independent call on every surviving row.
   - **What it reads.** The locked offer set for the row's `segment` (operator decision 2026-09-22): `offer.segments[<segment>]` when the client has per-buyer-type offer sets, otherwise the top-level `offer` block. Judge the row against every offer in that set (the primary and its validation arms): `offer_fit = yes` when any of them can serve the company, `no` only when none can, with the fitting offer named in `offer_fit_reason`. For each offer, read its `lead_magnet` plus its detail fields (`offer.lead_magnet_details`, `offer.lead_magnet_cta_direction`, `offer.lead_magnet_gap`) in `client-profile.yaml`, and the selected magnet's write-up in `lead-magnets.md`. Judge it against the same free text Tier 1 already has in hand (the discovery source's description, keywords and business-model fields, plus the free homepage text), so this is a second question on an existing pass: **no extra crawl, no extra credit, no new tool.**
   - **What it writes.** `offer_fit` (`yes`|`no`|`unclear`) and a one-sentence `offer_fit_reason`, on every row. Like `hard_no` below, this is a first-class machine-checkable column rather than a buried note, because the gate report has to count it.
   - **How it resolves.** `offer_fit = no` resolves the row to `fit_status: bad`, and it is dropped before Layer 1b enrichment spend. **`unclear` NEVER drops a row on its own:** route it through the same Tier-2 escalation that low `fit_confidence` rows already use, and if the deeper pages still cannot settle it, the row survives on whatever the ICP verdict says. An ambiguity bucket that quietly resolved to "drop" would itself be the starvation mechanism the reporting guard below exists to catch, and it would contradict this skill's conservative default of gating only what is clearly `bad`.
   - **HARD precondition: no locked offer, no offer-fit gate.** This judgement is unanswerable without an offer, so it is not optional and it has no fallback. If the row's segment has no locked set and the top-level `offer.lead_magnet` is missing or empty, STOP and route back to the offer work (see Stop Gates). **Never silently score ICP-only and continue:** that spends Layer 1b enrichment money on companies the offer cannot serve, which is the exact leak this gate closes. `offer.lead_magnet: direct_offer` IS a locked offer (the offer-first play that carries a direct CTA instead of a separate magnet): apply the gate question to the underlying service that CTA sells.

   **Binding meaning: `bad` now has TWO causes, and either one drops the row before Layer 1b enrichment spend.**
   1. **Outside-market by ICP.** A genuinely outside-market company, wrong entity, or no plausible customer relationship.
   2. **Cannot use the offer (`offer_fit = no`).** The business cannot use, stock, deploy, or buy what the locked offer delivers, so there is nothing to sell it this wave even where the firmographics look right.

   Adjacent industries, serviceable sizes, expansion geographies, and other real but imperfect prospects remain `maybe` under both causes, and an `unclear` offer-fit read never drops a row by itself. This is an enrichment-spend gate, not the final 10-point priority score. **Record which cause fired in `fit_reason` and keep `offer_fit` on the row**, because the gate report below has to count the two causes separately and cannot reconstruct them afterwards from a merged verdict.

**Free ride-along on the same classify pass: the `sold_to` axis (who the company sells to).** The Tier-1 on-disk classify already holds the text needed to read the company's *own* customers (the discovery source's description, keywords and business-model fields, the company-data provider's company description, and the free homepage text). Emit the `sold_to` group in the **same** pass, for free: `sells_to_vertical` (text, their end-customer vertical in their own words), `sells_to_customer_size` (enum), `sells_to_department` (enum), `sells_to_motion` (enum). These are `fill_method = derived` (a classification, like `sales_motion`), `gate_role = n/a`, no per-company credit and no new crawl. Coverage is honestly `med` (many B2B firms state who they serve; some only imply it). They join onto contacts as `co_sells_to_*` in Layer 1d and are the **highest-leverage message-differential axis** `/campaign-strategy` slices on (the "list is the message" doctrine). Because the inputs are the qualify-layer text, they are available even on the Phase A sample.

#### The fit gate (between Layer 1a and 1b)

**Hard-no categories: auto-DQ plus a `hard_no` column (before the good/maybe/bad gate).** If the client profile lists `icp_hard_filters.hard_no_categories` (or `industries_out`), emit a **`hard_no` column** on `tam.csv` (the category name, e.g. `dental`/`veterinary`, or blank) and treat any non-blank `hard_no` as an automatic DQ: set `enrichment_tier = qualified_out`, and **every campaign slice MUST exclude `hard_no != ""`** so these never reach the client's reps. **Match on NAME + DOMAIN only**, never keywords/specialties (a multi-service health system that merely *offers* a dental or vet clinic is NOT a dental/vet practice; matching its keyword blob over-DQs real ICP accounts, verified on a client build 2026-06-13, where a keyword scan flagged 290 false positives vs 23 true name/domain hits). Why this matters: discovery sources mislabel adjacent verticals into the ICP (a broad `HEALTHCARE` category explicitly includes dental practices; veterinary leaks in via lookalike), and a hard-no that reaches the client's AEs is a delivery miss that does not count. This is the client-requested "hard-no scoring column": keep it as a first-class, machine-checkable filter, not a buried note.

Then, on the rows that pass the hard-no filter: keep `good` and `maybe`; gate out `bad`. Set `enrichment_tier = enriched` on the survivors and `enrichment_tier = qualified_out` on the rest. **Gated-out rows stay in `tam.csv`** with their `qualify` columns and a `fit_reason`, extension columns left blank, never deleted, so a later wave or a loosened ICP can revive them (same philosophy as `in_reserve`). **On high-stakes lists, spot-check a sample of the `qualified_out` (`bad`) rows before trusting the gate:** a native discovery-source scorer is typically ~98% accurate but its rare misses are **false-negatives** (it marks `bad` a company that actually fits), so a quick crawl-plus-classify re-check of the gated-out sample recovers the few good ones it dropped. Spot-check the `bad` verdicts, not the `maybe`s. **Sample the TWO drop causes separately, because a new gate does not inherit the old gate's track record.** Draw one sample from the rows dropped on ICP fit and a second, independent sample from the rows dropped on `offer_fit = no`, and re-check each against its own question: the ICP sample against "is this the kind of company the client sells to," the offer-fit sample against "can this business actually use, stock, deploy, or buy what the offer delivers." A single merged `bad` sample hides an offer-fit gate that is mis-firing, because the ICP drops usually outnumber the offer drops and would dominate the sample. If the offer-fit sample surfaces real recoveries, the criterion is too tight: loosen it and re-run the gate before spending on enrichment, rather than accepting a thinner survivor set. Under `auto_execute`, enrich `good`+`maybe` and gate only `bad` (the conservative default; it minimizes false drops); report the good/maybe/bad counts and the estimated per-record enrichment spend the gate saved. Under `review_gates`, show the counts plus a labeled good/maybe/bad sample and let the operator confirm or move the threshold before any extension spend.

#### Gate reporting: the survival ledger (MANDATORY, do not omit)

**A hard gate can starve a launch slice silently, and that is the known failure mode of this one.** The totals stay healthy in aggregate while one segment quietly falls under the volume it needs to launch, and nobody finds out until `/campaign-strategy` cannot build a wave from it, long after the enrichment money is spent. So **the gate does not count as run until its ledger is reported.** This is the verify-before-done rule applied to the gate: the gate returning a clean number is acceptance, not proof of outcome, and the outcome that matters is whether every slice still has enough companies left to launch.

**Report this ledger per segment AND per group, every time the gate runs:**

| Field | Meaning |
|---|---|
| `companies_in` | rows entering the gate for this segment / group |
| `dropped_icp_fit` | dropped as outside-market by ICP |
| `dropped_offer_fit` | dropped on `offer_fit = no`, so they cannot use, stock, deploy, or buy what the offer delivers |
| `survivors` | rows carried into Layer 1b (`enrichment_tier = enriched`) |

Count each dropped company **once**, under the cause recorded in its `fit_reason`, so the numbers reconcile exactly: `companies_in` = `dropped_icp_fit` + `dropped_offer_fit` + `survivors`. A row failing both tests counts under offer fit. A ledger that does not reconcile means the drop cause was not recorded per row, which is a build defect to fix before enriching, not a discrepancy to explain away.

**The sub-floor alarm. If any slice lands under the ≥500-company eligibility floor, say so LOUDLY at the TOP of the report, and name the offer-fit gate as the cause.** That floor is `/campaign-strategy`'s HARD RULE (operator directive 2026-07-12), the same floor the Signal Coverage Table further down is read against, so a slice that finishes below it is not a smaller campaign, it is a campaign that cannot launch. The alarm is the **first line of `tam-build-report.md`, above the counts table**, written in plain words ("WARNING: the <segment> slice has 340 survivors, under the ≥500-company floor. The offer-fit gate dropped 620 of 960 companies"). Never a footnote, never a cell in the ledger table, never left to the reader to notice by comparing two numbers. **A slice must never be allowed to starve quietly.**

**When the alarm fires, name the two real remedies and recommend one.** Per this skill's Material Decision Rule, do not silently accept a starved slice and do not silently widen to fix it:

1. **Relax the offer-fit criterion.** Loosen what counts as `offer_fit = no`, push the borderline cases back to `unclear` (which survives), and re-run the gate. **Recommended first**, because the gate is a classification over text already on disk: re-running it is free and fully reversible, and a gate tuned slightly too tight is the more common cause of a starved slice than a genuinely dead market.
2. **Widen the segment.** Climb the expansion-for-volume ladder above (more or stronger seeds, looser similarity, more geographies, wider headcount bands, merge sibling groups, then the broad-filter expansion top-up) to bring more companies into the gate. Weaker as a first move because it costs real discovery spend and it cannot help at all when the offer-fit gate, not the company count, is what emptied the slice. Reach for it once remedy 1 has been tried and the survivor count is still short.

If neither clears the floor, report that honestly: this segment does not support a launchable campaign for this offer. That is a real finding the operator needs, and it is a far better outcome than a sub-floor campaign built quietly on a starved slice.

**Phase A and Phase B fire this differently, and both matter.** In **Phase A** the sample is bounded by construction, so a raw survivor count under 500 means nothing and a hard flag there would cry wolf on every run. Report instead the **offer-fit drop rate** and the **projected full-universe survivor count** ("offer fit removed 38% of the sample, projecting roughly N survivors across the full universe, under the 500 floor"). That projection is the more valuable warning, because it lands **before** the Phase B enrichment spend, while relaxing the criterion is still free. In **Phase B** the counts are real, so the hard sub-floor alarm above fires on the actual survivor count.

### Layer 1b: enrich the survivors only (the expensive beyond-source signals)

Run enrichment **only on `enrichment_tier = enriched` rows** (`good` + `maybe`); this is where the per-record/per-page money is, so gating it to good-fit is the saving. **Tool priority: the company-data provider first, then the discovery source's native enrichers, then the rest of the light stack (web crawl / web search / paid scraper / people-database company endpoints).**

> **Primary-provider-first, exhaust-then-gap-fill. HARD RULE (operator directive 2026-06-29).** For every `enrich` column the company-data provider *can* return, **run that provider across the WHOLE survivor set first, then route ONLY the cells it left blank** (plus the columns it has no field for at all) to the next tool. Never open a paid fallback on a column the primary provider covers until the primary has had its pass and you know which cells are actually still empty. The fallback tools fill *only the gaps*. This is the company-level twin of the contact-level rule already binding in `/email-waterfall` (the finder finds first, the waterfall enricher is residue-only), and its purpose is identical: never pay a second tool for data the cheap-first tool already returned. **Scope, honestly:** the saving is real but **column-scoped**. It only bites where the primary provider and a paid fallback *overlap*. Typically-covered `enrich` columns are `is_hiring_now` / hiring titles (`job_posting_*`), `has_public_pricing` / `has_demo_cta` / `has_contact_sales_cta`, `technologies_used`, web-traffic, and funding; web-crawl-only signals (proof/case-studies detail, news triggers, industry-idiosyncratic columns) have no provider field, so there is nothing to "fill first" and they go straight to their one cheapest-capable tool. Treat this as a routing discipline on the overlap columns, not new machinery. (The cheap-qualify-before-enrich gate still runs first: firmographics arrive free with discovery and feed the `fit_status` score, so you never pay per-record on a bad-fit company.) Claude pulls what the company-data provider and the discovery source's native enrichers return (source-native, see below). **By default (`seat_a`) Seat A then collects the beyond-source columns itself** (enrich-crawls, paid-scraper ads, org-depth, external web search; steps 5-7 below) via the fast crawl in this layer, going straight to step 8 (derive) when done. **Only under the operator's `seat_a_then_revcode` choice** are those beyond-source columns instead routed to the external enrichment platform via the **Layer 1c** copy-paste handoff (the operator runs them with their own integrations); on that path Claude resumes at step 8 once the external CSV returns. **For the beyond-source `enrich` columns (steps 5-7), pick the tool by the `/lead-list-tech-stack-research` Collection Routing Priority ladder (free public/official datasets -> web crawl (WebFetch) -> web search (WebSearch) -> a Claude Code sub-agent extraction) and use a paid scraper only where no lighter active tool returns the field. This holds whether Seat A collects them (`seat_a`) or the external platform does (`seat_a_then_revcode`).**

> **Run the Seat A enrichment crawl FAST (HARD RULE, enforce at run time).** The survivor crawl is the heaviest compute in the pipeline and it is **concurrency-bound, not per-site-bound** (a crawl returns in ~0.5s in any mode), so the tuned config below is the required default, not an optimization to remember. On every large enrich crawl use: the crawler's plain-HTTP request mode with **proxy off** first (escalate to a headless-browser mode only on a 0-page result), a page `limit` of 2, independent providers issued in parallel, and **~40 concurrent workers** (push toward the 429 knee, watching whichever provider throttles first). Measured ~9x over the naive smart-mode / limit-4 / serial / 16-worker default (~15 to ~133 rows/min, 0x429). **No AI model runs inside the crawl loop (no-AI-API rule, operator directive 2026-09-22):** the crawl writes page text to disk, and Claude Code sub-agents extract the fields afterwards in disjoint batches.
> **Runtime tripwire (this is the enforcement, not a note).** If the crawl is running below ~100 rows/min, STOP and fix the config before continuing: you almost certainly have the proxy on, a browser mode first instead of plain HTTP, `limit` above 2, or too few workers. A slow crawl is a misconfiguration, not the normal rate. Leaving the proxy enabled alone is an ~8-9x slowdown.
> **New enrich scripts MUST copy the proven pattern, never re-derive it from memory:** start from an existing enrich-crawl script in `scripts/` that already bakes in the ~40-worker concurrency, the hard fetch timeout, the http-to-browser escalation ladder, the credit floor, and resume-on-done, rather than writing a fresh crawl loop.
> **Kill any orphaned crawl process before relaunching** (a slept or relaunched job keeps appending to the same enrich journal file, wasting credits; resume-on-done makes the dupes harmless but kill it anyway). Full measured settings live in `/lead-list-tech-stack-research` section 7 (Fast-crawl settings).

**Source-native deeper calls are Claude's to pull, primary provider first, and are PREFERRED over any external tool where they cover the field.** A deeper native detail field on the SAME spine (the company-data provider's company-search rows, which already carry the deeper firmographics; the discovery source's own native enrichers, such as a company-profile detail call, a growth/trend call, a digital-footprint score, and a data-append call) is still source-native, so Claude pulls its full field set on survivors (gated). This is NOT the external scraping that goes to the external enrichment platform. **Check the company-data provider first** for any field, then the discovery source's native enrichers. For lookalike-sourced rows specifically, prefer its native enrichers over re-deriving the same field externally: a data-append call for revenue/employees/business-model/keywords, a growth/trend call for the multi-quarter headcount and footprint trend (the `headcount_trend` "why-now" signal, native), a digital-footprint score for the company-scale proxy. They reuse domains already discovered and avoid a second external per-record charge. Tech-stack/vendor fields are the common exception, since they are frequently gated off on lower plans: route those elsewhere per `/lead-list-tech-stack-research`.

5. **Crawl-derived enrich signals: Seat A by default (web crawl), external platform under `seat_a_then_revcode`** (`gate_role = enrich`): pricing tiers/prices, proof (case studies, customer logos, `named_customers`), security/compliance, via a multi-page crawl beyond the Layer 1a fit pass, on survivors only. **Primary provider first, though:** the pricing/demo/free-trial booleans and `technologies_used` come from the company-data provider; only the crawl-only detail needs the beyond-source tool (Seat A runs the crawl itself under `seat_a`; it goes to the external platform only under `seat_a_then_revcode`).
   - **`jd_pain_language` gets its own routed chain, because the page it needs is not on the company's own site: WebSearch finds the live job-posting URL (an ATS posting or the careers page), WebFetch reads that page, and a Claude Code sub-agent extracts the pain phrase from the job-description BODY.** This is the same route `/data-point-discovery` documents for this column (its Signal extension columns section), so keep the two consistent. It is the Collection Routing Priority ladder's own tools (crawl + search + a sub-agent extraction, no paid scraper and no other AI provider), just ordered search-first because the URL has to be found before the page can be crawled. The cell is `fill_method = scraped`: `source` = the tool that returned the page, `evidence_url` = the job-posting URL itself. It is a real scrape of a real page, not a derivation. No per-page vendor or AI cost applies on this chain; the constraint is session time. The crawl leg runs under the fast-crawl HARD RULE above, starting from a proven existing enrich script, never a fresh crawl loop. Why the column earns the crawl: `hiring_roles` only records that a role is open, while the JD body carries the problem in the buyer's own words, which is what makes this a copy variable ("the job description is far more valuable than the job post"; the rules for using it in copy live in `/campaign-copywriting`).
   - **Why the primary-provider-first HARD RULE does not stall this column.** The provider still runs first for `is_hiring_now` and the hiring titles (`job_posting_*`), exactly as the rule says. But those fields are title, seniority, type and location metadata; a company-data provider structurally cannot return the job-description body. So `jd_pain_language` is **not an overlap column**, has no cells for a provider pass to fill first, and routes straight to the search-then-crawl-then-extract chain above. A naive reading of the rule (wait for the provider on anything hiring-shaped) would hold this column behind a pass that can never fill it, which is how a scored `collect_now` column silently lands at 0% after the spend.
   - **Coverage is honestly low by construction, and the guessed-boolean trap that would hide it.** The cell fills only for a company carrying a live, crawlable posting at build time, so expect coverage **well below the firmographic columns**. Judge it against its predicted `coverage` in the Signal Coverage Table, exactly as the `change_timing` columns are judged, never against firmographic fill-rates. **HARD RULE: never substitute a generic AI "are they hiring for X roles?" boolean for the crawled text.** Those booleans **over-assert roughly 89% true at low context**, because the model cannot verify a negative (verified on a client why-now enrichment pass). A phrase produced that way is precisely the **guessed** cell the cell-kind rule below forbids: no scrape behind it, no `derived_from` basis, and a fabricated pain phrase is indistinguishable from a real one once it sits in the column. The phrase comes from the ACTUAL crawled JD text, or the cell stays blank. Quote only live, publicly accessible JD content.

Pure logic, Claude-Code-native; **never** a paid call and **never** a fresh fetch. #### Bulk contact discovery at lookalike scale (hundreds+ companies)

A single conversational call to a domain-scoped contact search often only covers a handful of companies well (its per-call result budget), so a lookalike-scale company list (the normal Layer 1d input, hundreds of survivors) needs a real bulk pattern, not a long loop of individual calls in the live conversation. Looping it in-context is also what actually killed past runs: a 2026-07-07 contact-discovery pass died mid-way when the session hit its account usage limit at batch 13 of 22, because a long single-conversation loop has no checkpoint, so an interruption loses the whole run.

**Use the same disjoint-subagent fan-out already proven in `/personalization-subagent-pattern`, applied to discovery instead of copy generation. First confirm the chosen contact source is safe to call concurrently: some single-account, single-domain-per-call APIs silently return another domain's rows under concurrency, and where that is true this step is serial-only and must NOT be fanned out.**

1. **Chunk the survivor company-domain list into groups of ~12-15 domains, and WRITE the chunk plan to disk before fanning out** (`profiles/<business-slug>/tam/contact-discovery-plan.json`, an ordered array of `{batch_id, domains: [...]}`, derived deterministically from the survivor list's existing order, e.g. `tam.csv` row order, never re-chunked from scratch on a resume, or batch numbering drifts and the resumability in step 3 breaks). Each chunk becomes one Task sub-agent's assignment (internally, that sub-agent makes a few sequential contact-search calls within the tool's per-call domain budget).
2. **Fan out 3-10 sub-agents in parallel per round** (same concurrency guidance as the personalization pattern). Each sub-agent's prompt: the ICP title filter plus exclusion keywords for this client's buying-committee roles, its `batch_id` and domain slice from the plan file, and an instruction to retry any zero-result company once with a widened title net (Managing Director / General Manager / Head of) before accepting it as a genuine null.
3. **Each sub-agent writes its own output file immediately, named by its `batch_id`** (`/tmp/contacts-batch-<batch_id>.json`), never a shared file. **This is the concrete resumability mechanism, not just the no-duplicate-output guard:** before spawning any sub-agent, list which `/tmp/contacts-batch-*.json` files already exist and diff that against the plan file's full `batch_id` list, then spawn sub-agents ONLY for the missing batch_ids. If a session is interrupted (session limit, connector hiccup) partway through, a fresh session re-reads the SAME plan file, re-runs this diff, and picks up exactly where it left off: it does not re-chunk the survivor list or guess which batches ran. This is the direct fix for the failure mode that killed a past contact-discovery run at batch 13 of 22 (a session-limit hit mid-loop with no checkpoint to resume from).
4. **Merge, dedupe, and report coverage in THREE buckets, not two.** After all batches land: merge by `company_domain`, dedupe contacts by the source's stable person id. **A small 9-company test (2026-07-12, collision-prone sample) found a third of "matches" were wrong-entity name collisions**: a real, confidently-titled person who belongs to a different company than the one searched. That specific rate is too small a sample to treat as a planning constant, but the failure mode itself is real and recurring enough that "found a contact" and "found the RIGHT contact" cannot be treated as the same bucket. For each company sanity-check the match (tenure/seniority against the company's real founding date and scale; a quick independent web check on `name + company name` when it matters) and classify: **found** (verified match), **wrong_entity** (a person surfaced but does not check out, so do not ship this contact), or **genuine_zero** (no match even after the widened-title retry). Report all three counts to the operator (X found, Y wrong-entity excluded rather than silently dropped, Z genuine zero) rather than collapsing to a single coverage percentage that hides which companies actually got a usable contact.

This mirrors `/personalization-subagent-pattern`'s three-layer no-duplicate guard (disjoint inputs, disjoint output targets, post-merge uniqueness check); read that skill for the full mechanics if building this fan-out for the first time on a client.

The gate is not finished until the ledger is reported (see Gate reporting above).
6. **Enrich the `gate_role = enrich` `collect_now` columns on `enriched` rows only (Layer 1b steps 5-7).** Claude pulls the source-native columns first (the company-data provider, then the discovery source's native enrichers), batched in catalog `rank` order, gated by `/api-cost-governance`. **By default (`seat_a`) Seat A then collects the beyond-source columns itself** via the Layer 1b fast crawl (web crawl / web search / paid scraper / people-database company endpoints). **Only under `seat_a_then_revcode`** does it instead generate the external handoff prompt (the non-source columns plus the primary-provider-first tool for each), present it, **BLOCK** for the returned CSV, and join it on `company_domain`. Leave `in_reserve` columns uncollected. `is_hiring_now` / `hiring_sales_roles` come free from the hiring fields already in the company-search response.
7. **Derive + normalize (Claude).** Once enrichment is in (step 6: Seat A's pulls, or the joined external CSV), **derive** every `fill_method = derived` column for free from the source-native plus enriched columns (Layer 1b, step 8), recording each value's `derived_from` basis; then normalize text with Claude Code sub-agents (Layer 1b, step 9). Record AI provenance. A derived cell whose inputs are blank stays blank. Derive `funded_last_90d` / `days_since_funding` from `last_funding_date` here; the refresh-delta change/timing columns (`funding_stage_changed`, `headcount_trend`, `hiring_velocity_change`, `pricing_changed_90d`, `added_tech_90d`, `dropped_tech_90d`, `started_ads_90d`) stay blank on a first build and are filled by the Monthly Refresh diff.
8. Write `tam.csv` + the data dictionary and the build report. **Phase B only.** Push the finished `tam.csv` to the list workbench (`--table companies --stage company_tam`) and, once `contacts.csv` is written, push it too (`--table contacts --stage contact_tam`), putting each push's N/N row count in the build report (or the CSV-only fallback line when a table is not ready). Set `run_state.status.tam_stage: full_enriched` and `run_state.tam_last_refreshed` ONLY once the full qualified universe and contact TAM are complete. Set `run_state.status.scoring_stage: none` because the new TAM has not yet been scored. In Phase A, set `tam_stage: sample_built`, push the sample (`--table companies --stage sample`), and hold at the GO gate.

**SOURCE-NATIVE EXTENSIONS (auto-included, free: capture by default, never trim).** Every field the discovery tool returned that has no STABLE-CORE canonical name is kept as its own column, named after the source field, e.g. web-traffic fields (monthly visits, global/category rank, bounce rate, pages per visit), capability booleans (documentation exists, downloadable, mobile apps exist, online reviews exist), classification codes (SIC, NAICS), top topics, and any similarity, footprint or appended score the source returns. These are `fill_method = scraped` with `source = <tool>`; they are captured automatically (the catalog does NOT need to list them) and are never trimmed to a subset. Record each in `tam-data-dictionary.md` as it appears in the build. `/campaign-strategy` may slice on them like any other column.

Each extension column carries its `fill_method` (`scraped` | `derived`) and, for derived columns, its `derived_from` input columns — recorded per column in `tam-data-dictionary.md`. The derivation rule is identical for every row, so it lives in the dictionary, not as a repeated `tam.csv` column; `tam.csv`'s STABLE CORE stays byte-for-byte as above so downstream skills do not break. Per-row traceability still holds because every `derived_from` input is itself a collected `tam.csv` column: any derived cell can be re-computed and checked against the real scrape behind it.

`source` and `evidence_url` keep the canonical names owned by `/lead-source-strategy` so the per-campaign pipeline (which adds the contact columns in Layer 2) stays compatible.

**Every cell is exactly one of two kinds — never a third:**

- **scraped** — a tool pulled it; it carries a real `source` and `evidence_url`. Never overclaim a weak crawl signal — leave a scraped cell blank rather than guess.
- **derived** — computed for free from columns already in the row; it carries a recorded `derived_from` basis naming those input columns (in `tam-data-dictionary.md`), mirroring how a scraped cell carries `evidence_url`. A derived cell whose inputs are blank stays blank.

The forbidden third kind is a **guessed** cell: a value inferred with neither a scrape behind it nor a named set of in-row source columns. A guessed true/false looks identical to a real one and makes the whole TAM look clean while being partly fiction. A derived column with no recorded `derived_from` basis is a guess — reject it, do not write it.

**Controlled vocabulary is catalog-owned — this skill no longer declares enums inline.** Enum and range values — `sales_motion`, `funding_stage`, `headcount_range`, `revenue_range`, `arr_range`, `headcount_trend`, `sales_headcount_growth_6mo`, `hiring_velocity_change`, and any client-specific enum/range — are defined in `/data-point-discovery`'s Schema Contract (fixed core buckets) and the catalog table's `allowed_values` column (extensions). Write those exact values/buckets; do not invent per-build boundaries — cross-segment compare depends on identical buckets. The fixed core buckets live in the `/data-point-discovery` skill itself (always available, even when building the STABLE CORE without a per-client catalog).

**The build report OPENS with the gate ledger, and, whenever any slice finished short, with the sub-floor alarm sitting above it.** Per Gate reporting, that alarm is the report's FIRST line, above the counts table, in plain words, naming the offer-fit gate as the cause and carrying the two remedies. It is never folded into the paragraphs below and never reduced to a cell in a table.

The build report must include: companies discovered per segment; **the fit gate — `good` / `maybe` / `bad` counts (and % of the discovered universe gated out), the per-segment and per-group survival ledger (`companies_in` / `dropped_icp_fit` / `dropped_offer_fit` / `survivors`, reconciling exactly), plus the estimated per-record enrichment spend the gate saved by not enriching `qualified_out` rows**; columns actually enriched vs deferred; a **Signal Coverage Table — per-column actual fill-rate (count + %) computed over `enriched` rows only** for **every sliceable signal column** (all `collect_now` columns — both `gate_role = qualify` and `enrich` — plus the source-native extension columns `/campaign-strategy` can slice on), NOT over the whole TAM, since `qualified_out` rows are blank by design and would corrupt the fill-rate signal, compared against the catalog's predicted `coverage` when present — this validates the discovery prediction, improves coverage estimates over time, **AND is the coverage table `/campaign-strategy` reads to choose and maximize the launch wave** (every signal **≥500 enriched companies carry** is a launch candidate — the **≥500-company signal floor**, `/campaign-strategy`'s HARD RULE, raised from the retired ≥100 floor by operator directive 2026-07-12; the per-signal count must be directly readable here so that test is mechanical; coverage sets launch *order* under capacity, never a rank-and-cut that would drop viable sparse high-intent signals); **any deferred `worth_a_fight` column named explicitly** (high-value points dropped for budget, so they are not silently lost); per-provider spend (estimate + actual via `/api-cost-governance`); and any segment crawled only partially (with what was skipped and why). Flag any `collect_now` column whose actual fill-rate lands materially below its predicted `coverage` (e.g. predicted high, actual <50%) as a coverage miss to correct on the next discovery pass. `change_timing` columns are expected to be the sparsest (a trigger is true for only a few companies at any moment) — judge them against their predicted `coverage`, not against firmographic fill-rates. For every column, record its `fill_method`; for each **derived** column, record its `derived_from` basis and confirm every named input is present in `tam.csv`. A derived column with no recorded basis, or one naming an absent input, is a guess — a QA defect to blank or fix before the build is marked complete.

## Monthly Refresh

TAM data goes stale. Refresh on a cadence (the note's Phase 2 maintenance), cost-gated each time. **Refresh `enrichment_tier = enriched` rows only** — re-pulling `enrich` columns for `qualified_out` companies would reintroduce the exact spend the fit gate avoided. Re-scoring `qualified_out` rows that may now fit (ICP loosened, or the company changed) is a deliberate later-wave re-qualification, not part of the monthly refresh.

- **Monthly:** volatile signals — running ads, hiring roles/velocity, pricing changes, new case studies, new companies in the universe.
- **Quarterly:** stable firmographics — headcount, funding, location.

**Capture the delta, do not just overwrite.** The refresh already re-pulls the volatile signals; computing what *changed* since the prior build manufactures the `change_timing` columns for near-zero extra cost. On each refresh, diff the new pull against the stored row and set: `pricing_changed_90d` (pricing differs), `added_tech_90d` / `dropped_tech_90d` (`tech_stack` gained/lost an entry), `started_ads_90d` (a `running_*_ads` flag flipped on), `headcount_trend` and `hiring_velocity_change` (direction vs prior), `funding_stage_changed` (stage advanced), and recompute `funded_last_90d` / `days_since_funding` from `last_funding_date`. Keep the prior values needed for the diff (or a small per-row history) so the comparison is possible; a first build with no prior leaves these blank rather than guessing.

Stamp `last_refreshed` per row. After each monthly refresh, invoke `/lead-scoring` to recalculate the strongest timing signal and the total score. Recalculate stable fit components only when the ICP, offer, segment mapping, or stable firmographics changed. A scheduled refresh routine may invoke this skill; it must run `/api-cost-governance` first and fail loud on an empty or errored refresh.

## Stop Gates

- **Primary company list = a case-study-seeded lookalike (PROVEN, DEFAULT) or a broad ICP filter (EXPANSION), per the Case-Study-Anchored Discovery HARD RULE, not a free operator pick.** The proven motion seeds a lookalike from the group's case-study companies (`/social-proof-bank`); the expansion motion uses a broad ICP filter (a filter-based company search, or a category / natural-language ICP query) for net-new segments or a brand-new offer with no proof. **The company-data provider is the ENRICHMENT layer, never the discovery spine.** Every other tool (WebSearch, the web crawl, paid scrapers, vertical revenue databases, people-database company endpoints) is **extension/augmentation** layered on top (firmographics, crawl signals, ARR, org-depth, demand), never the primary spine. Exceptions: a genuinely local-SMB / maps-first universe is its own list-building motion, and a signal-first list (scraping a directory, job board or event as the source of truth) is the `/lead-source-strategy` Lead Source Plan Mode motion; neither is this firmographic TAM spine.
- **Offer not locked, so the offer-fit gate cannot be evaluated.** Layer 1a asks whether a business can actually use, stock, deploy, or buy what the offer delivers, and that question is unanswerable with no offer on record. If no offer set is locked in `client-profile.yaml` (neither `offer.lead_magnet` nor any `offer.segments` entry), STOP and route back to the offer work (`/lead-magnet-brainstorm`, or `/offer-intelligence` first when no candidate set exists yet) before discovering or classifying anything. **Never silently fall back to ICP-only scoring.** That is precisely the failure this gate exists to prevent: the build looks normal, and it quietly spends Layer 1b enrichment money on companies the offer cannot serve. `offer.lead_magnet: direct_offer` IS a locked offer (the offer-first play carries a direct CTA instead of a separate magnet), so apply the gate question to the underlying service that CTA sells rather than treating the sentinel as a missing offer.
- **Offer-fit gate reporting is not optional.** The gate counts as run only once the per-segment and per-group survival ledger is reported, with the sub-floor alarm at the TOP of the report whenever a slice lands under the ≥500-company eligibility floor. A gate that silently starves a launch slice has failed, even when every single row it dropped was dropped correctly.
- **No enrich spend before the fit gate.** Do not collect any `gate_role = enrich` column until Layer 1a has scored `fit_status` across the TAM and the gate has been applied. Per-record enrichment (org-depth, ads, company-provider detail) on the whole un-gated universe is the exact waste this skill exists to prevent.
- **Never delete a gated-out company.** `qualified_out` rows stay in `tam.csv` with their `qualify` columns + `fit_reason` so a later wave or a loosened ICP can revive them; gating means "don't enrich," not "discard."
- **No per-contact spend here.** If a step would reveal or verify a person's email/phone, stop — that belongs to `/email-waterfall` on a live slice.
- **By default (`seat_a`) Seat A does discovery + fit + ALL enrichment; the external enrichment platform is the operator's optional `seat_a_then_revcode` choice.** Claude runs the Layer 1a fit decision itself (cheap native classify off the discovery source's returned text plus its free homepage extraction, via Claude Code sub-agents over disjoint batches; a crawl escalates only the ambiguous rows), pulls source-native enrichment from the company-data provider (first) and the discovery source's native enrichers, and, under the default `seat_a` path, collects the beyond-source columns (crawls, ad-library scrapes, org-depth, external web search) itself via the Layer 1b fast crawl. **Only when the operator picks `seat_a_then_revcode` at the GO gate** are those beyond-source columns routed to the external enrichment platform via the Layer 1c handoff instead; on that path, BLOCK for the returned CSV, never synthesize those columns yourself, and never start `/campaign-strategy` while blocked.
- **Spend ceiling (the one valve on completeness).** If the Layer-1 estimate to collect the full obtainable set meets or exceeds `run_state.spend_ceiling_usd` (the standing $100 per client run unless the operator set another figure), stop and surface it — the default recommendation is to **raise the ceiling to cover full collection** (completeness is the goal); trim by rank only on the operator's explicit say-so, never silently dropping obtainable signals.
- **Paid collection stays inside the ceiling, not inside a campaign.** The gate is on *paid collection* and on the ceiling, NOT on whether a campaign has asked for the column yet — under the Collection Completeness rule the full `collect_now` (all-obtainable) set is collected up front by default. What still needs operator approval is (a) collecting an `in_reserve` exception that was previously cut, or (b) any collection whose previewed cost exceeds `run_state.spend_ceiling_usd` (surface it, default to recommending the ceiling be raised to cover full collection).
- **A list workbench push that falls short is never silently accepted.** If a push lands fewer rows than its CSV holds, report the shortfall at the TOP of the build report and retry once, re-pushing only the rows that failed (never the whole CSV again, because a webhook push appends and a full re-push would duplicate the rows that already landed). Report the retry's N/N either way. A workbench that is not ready is NOT a stop gate: it is the CSV-only fallback in the List workbench rule.
- **Missing data-point catalog.** If `data-point-catalog.md` does not exist, there is no contract to collect against — build the STABLE CORE only and route back to `/data-point-discovery` before collecting any extension columns.
