# TAM Build (company-level, up front)

**From the former description:** Classify the company universe against BOTH the ICP and the LOCKED offer before expensive enrichment: a company that cannot use, stock, deploy, or buy what the offer delivers is bad and is dropped before enrichment spend, while genuinely adjacent marketable companies stay maybe. Requires a locked offer, and reports per segment and per group how many companies each gate dropped. Discover every plausible buying role across good and maybe companies without revealing or verifying email. Runs after /data-point-discovery and before /lead-scoring (when scoring is required); refreshes monthly. Gated by /api-cost-governance.

Build the client's whole addressable company and contact universe once, up front. First build a bounded sample, then the full universe after the GO gate. Once both TAMs are complete, `/lead-scoring` turns them into a ranked P1 through P5 queue when sending capacity forces a cut; a first wave that ships every tier may skip it (`/phase-3-list` step 3). `/campaign-strategy` runs after that score is complete, or straight after the TAM when scoring is skipped.

The cost trick is two splits, not one. **(1) Company-level vs per-contact:** everything here is company-level (discovery + web crawl + company databases + Claude Code sub-agent normalization), which is flat/per-page cheap; the expensive per-contact layer (verified email, phone, verification) is deferred to the live slice in `/email-waterfall`. **(2) Qualify vs enrich, *within* the company layer:** discover the universe and capture the full source-native field set, score ICP fit (good/maybe/bad) cheaply from the discovery source's already-returned text plus any free homepage text it exposes (Claude Code sub-agents fanned out over disjoint batches do the classify; a web crawl only escalates the ambiguous rows, never every company), then collect the expensive beyond-source signals (org-depth, ads, multi-page proof/pricing/careers) **only on the companies that pass the fit gate** (Seat A enriches them hands-free via its own tools by default; the operator can instead finish them in an external enrichment round-trip). Qualify it cheap; pay to enrich only the good-fit slice, and pay for contact emails only on the slice that goes live (in the first wave that is every eligible contact in Aaron's launch set, `/phase-3-list` step 5, operator directives 2026-09-22 and 2026-09-28). (This qualify-then-enrich mechanic runs on a bounded **sample** in Phase A and on the **full universe** in Phase B, see the HARD RULE below, never blindly on "the whole TAM in one shot.")

## TAM-First Sequencing. HARD RULE (sample -> GO -> full + enrich -> THEN campaigns)

The whole point of building the TAM up front is that **campaigns are sliced from data points that actually exist in the list.** So the TAM must be fully mapped (every qualified company discovered and fit-scored, its free Layer-1 fields and default set captured, and its ICP decision-makers discovered) *before* any campaign idea is generated or any approval brief is written, never the other way around. Outputting campaign ideas without knowing the real, available data points of the actual lead list is the exact failure this rule prevents. This gate is binding and applies regardless of `execution_mode`. **Signal enrichment is not part of this gate** (Aaron process alignment, operator directive 2026-09-22; supersedes the 2026-06-29 "with all signals" reading): Aaron maps the TAM and sends it without waiting on signal columns (Sep 14: "there's no reason not to start with the simplest method of pulling a lead list if you have a really good offer"), so the first wave never waits on a signal column.

**Pull the whole market, judge only the wave (list speed rules, operator directive 2026-09-26).** The pull is cheap and fast. The slow and paid judgment (the fit classify, headcount cross-checks, the title AI pass) and the paid enrichment run only on the scope of the wave being built. For the whole-TAM first wave that scope is every pulled company; each later wave (`/campaign-strategy`) judges its own scope from the same pull, never the whole market again. Judgment over many rows is always a parallel Claude sub-agent fan-out (Layer 1a step 4), never a serial loop in the main conversation and never a third-party AI API.

**`run_state.status.tam_stage` is the single source of truth for where the TAM is** (this replaces the old `complete` value, which was ambiguous: `complete` previously meant only "a sample was built" and must no longer be used):

| `tam_stage` | Meaning | What may run next |
|---|---|---|
| `none` | not started | `/data-point-discovery`, then this skill (Phase A) |
| `sample_built` | a bounded **sample** is built + qualified; seed/ICP fit validated; this is **NOT the full universe** | hold at the GO gate below (auto-approves within ceiling under `auto_execute`, else stops); nothing downstream may run until `full_enriched` |
| `full_enriched` | the **whole qualified universe** mapped, fit-scored (ICP + offer) and its contacts discovered; signal columns are optional for this stage (Aaron process alignment, operator directive 2026-09-22). Company and contact TAMs are complete, with the default set (free Layer-1 fields, derived columns, fit and offer-relevance fields) captured on the same pass; a paid signal the catalog marks `collect_now` is collected alongside when it fits the budget, and one still filling or trimmed never holds this flag | `/lead-scoring` when scoring is required, then `/campaign-strategy` |

**Phase A: sample build and validate, then `tam_stage: sample_built`.** Build a **bounded** sample, attach cheap firmographics plus the Tier-1 cheap fit classify (the discovery source's returned text plus any free homepage text it exposes), score `fit_status`, and confirm two things: the fit-rate is sane (**tune the query to 80%+ sample fit before scaling**, measured on ICP fit, which is what the query actually controls, with the offer-fit drop rate reported separately per Gate reporting because no amount of query tuning fixes a market that cannot use the offer; per the discovery-source validation rubric: 80%+ means stop tuning and do not over-tweak a good query; 75-80 means minor tweaks; under 50 means rework from scratch) and the filters (or seeds, on the lookalike route) and ICP converge on ONE offer-fit population rather than a contaminated list: one vertical when the offer is vertical, and for a horizontal offer the population the offer fits across industries, judged by offer fit rather than by one industry (Aaron process alignment, operator directive 2026-09-22; Aaron, Sep 14: "Whether it was e-commerce, SAS, agencies, didn't really matter"); and the priority `collect_now` data points are actually collectable for this population. A sample is ALWAYS bounded, never the full pull. What bounds it depends on the discovery route (Filter-First Discovery HARD RULE below):
> - **Filter route, the DEFAULT (operator decision 2026-09-28):** one query can return the *entire* universe at once, so there is no natural sample. Cap it explicitly. Size the universe first without pulling it: resolve the enums with the company-discovery source's industry, technology and location lookups, read its `company_search` `totalElements` with the list's filters and keyword stack (`provider-routing.yaml` `layers.company_discovery` `sample`), and once the search is refined read the list source's `count_contacts` on it (an exact count, not a pull). Pull only a bounded slice for Phase A (e.g. the first ~300 companies, or a representative spread across the key firmographic bands and segments), tune the keyword stack and filters on it, and leave the full pull for Phase B. **Under the house order (the default; operator directive 2026-10-06, see `standing-rulings.md` `discovery-flow`) the bounded slice is the vertical's AI Ark company sample of 200 to 300 companies, and the tuning is one keyword-mining pass** (`ai-ark-people-discovery.md` Step 1): every keyword and industry common to the good-fit companies becomes an include, every one common to the bad-fit companies an exclude, one common to both is used on neither side, and all of them are used, with no cap, no review round and no validation sample (company fit after the GetLeads export drops the bad rows).
> - **Lookalike route, the exception, only for a group that met both lookalike conditions:** the natural first discover batch (a few hundred companies) is the sample. **Use it to tune the discovery source's similarity threshold (and its variance/breadth control) to the point where the sample's fit-rate is acceptable BEFORE the full pull.** A lookalike tool's similarity score is the precision lever, so a well-set threshold means the full-universe fit pass has less to remove and you re-pay the per-record credit for fewer off-ICP rows. **Check the tool's unset defaults before your first pull: lookalike tools commonly default to their most permissive setting, which is not what you want.** Seed from the 5 to 10 companies that best fit the LOCKED offer (the group's offer-fit case-study/customer companies from `/social-proof-bank` first, topped up with researched offer-fit exemplars, within the 5-AI-plus-5-client seed rule and the tool's seed cap), and promote validated-`yes` companies to seeds as you tune.
>
> Present the sample, its fit-rate, the route taken, the projected size of the whole pull and of the wave's scope, and the projected enrichment cost of the wave's scope.

### Step 0: compile the targeting spec (before any discovery, added 2026-09-24)

The list build consumes a targeting spec; it never invents the ICP or the title list on the fly. Before Phase A, compile `profiles/<business-slug>/targeting-spec.yaml` from the template `<outbound>/reference/targeting-spec-template.yaml`, using only inputs that already exist:
- `icp_hard_filters`: headcount, geography, `industries_out` / `hard_no_categories`, and the `excluded_titles` and `excluded_domains` keys where the profile carries them;
- the locked offer's `offer.title_stack`, `offer.offer_fit_disqualifiers` and `offer.icp_inclusion` (per segment where `offer.segments` exists);
- the rubric's persona mappings, when a rubric already exists.

Turn the titles into function families with patterns, the buyer tiers (exact = buyer P1 through weak = buyer P5, the one buyer-priority scale), title and account exclusions, the generic-executive size rule, `contacts_per_account`, and the phone and personal-email policies. Record every source in `compiled_from` and set `status: locked`. The rulebook this spec feeds is `list-production-standard.md`.

- **When the spec cannot be built, stop before a large pull.** That means no locked offer, no buying function, or nothing a function family can be built from. Under `auto_execute` Claude compiles and locks the spec itself from those inputs and proceeds, so this adds no pause when the inputs exist.
- **The spec is the contract downstream.** `scripts/title_classify.py`, `scripts/list_waterfall.py` and `scripts/list_qa.py` all read it, so every later judgement about "is this the right person" traces back to one file.
- **Every change to it is logged** in its `changes` list with the reason, including the fixes the 25-account QA below forces.

### 25-account list QA (before any Phase B spend)

**This reviews the targeting logic before money is spent. It is never a sending pilot, and it never shrinks the first wave** (Aaron process alignment, operator directive 2026-09-22: the first wave still covers the whole qualified TAM). The fit gate scored the sample with the prompt it was tuned on, so its own verdicts cannot show whether the query, the prompt or the disqualifiers are wrong. A reviewer that never saw that prompt can.

- **Draw the 25.** After Phase A's sample is classified (Layer 1a steps 3-4), draw 25 accounts from it, stratified as closely as the sample allows: about 15 kept `good`, 7 kept `maybe`, and 3 dropped `bad`. When a stratum is short, take what it has, fill from the others, and say so.
- **An independent reviewer judges each account.** A fresh Claude Code sub-agent that did not score these rows gets only the ICP, the locked offer, `offer_fit_disqualifiers`, `icp_inclusion`, the geography, the headcount band and `industries_out`. The offer fields come from the row's segment, by the same rule the `offer_fit` judgement uses: `offer.segments[<segment>]` when the client has per-buyer-type offer sets, otherwise the top-level `offer` block. The reviewer never sees the fit prompt or the classifier's verdicts. It reads each company's own site (WebFetch) and checks five things: the buyer role plausibly exists there; the company is not in an excluded industry or domain; it is inside the geography; it is inside the size band; and it can use or buy the offer. Its verdict is `belongs` (all five hold) or `does not belong` (naming the check that failed), marked `excluded` when the failed check is the excluded industry or domain.
- **Agreement is scored at the kept-versus-dropped level.** `belongs` agrees with a kept row (`good` or `maybe`), and `does not belong` agrees with a dropped row (`bad`). The good-versus-maybe split is not scored, because that boundary is a priority call, not a targeting error.
- **Record it.** Write the 25 verdicts (domain, the gate's verdict, the reviewer's verdict and its reason), the agreement rate with the fit gate, and every disagreement with its reason in `tam/tam-build-report.md` under `## 25-account list QA`, placed after the survival ledger so the sub-floor alarm stays the report's first line. Set `run_state.status.list_qa_stage` (`none` | `passed` | `failed`).
- **PASS** = at least 20 of 25 agree AND no account the reviewer marks `excluded` was kept as `good`.
- **Buyer probe: the second half of the QA (added 2026-09-24).** The company check proves the accounts fit. It cannot show whether the title logic finds the right person, because no contact exists yet in Phase A. So on the accounts the reviewer marked `belongs`, run the first people-discovery rung in `provider-routing.yaml` `layers.people_discovery` (the contact-discovery source's people search: Layer-1 cost only, no email reveal), at the concurrency the routing file allows for that source (Layer 1d's concurrency-safety check applies here too). Its per-call cost is not yet verified, so preview it through `/api-cost-governance` like any paid call. Then classify every returned title with `scripts/title_classify.py` against `profiles/<business-slug>/targeting-spec.yaml`. Report four things, in the same `## 25-account list QA` section (and, under `review_gates`, beside the 25 rows at the GO gate):
  - the accounts where a target person (buyer tier exact or strong) was found;
  - the buyer-tier mix;
  - the most common failed and ambiguous titles;
  - false positives (a passing title at the wrong function) and missing variants (a title a person would call the buyer that the rules failed).

  **PASS** = a target person found at 12 or more of the probed accounts AND no false positive repeating 3 or more times. On FAIL, fix the targeting spec (families, patterns, explicit titles, exclusions; log each change), re-classify, and re-probe, within the same two fix rounds as the company check. `list_qa_stage` is `passed` only when both halves pass. Fixing the title logic here, on 25 accounts, is what stops a 20,000-row pull from needing to be filtered afterward.
- **On FAIL, fix the cause and re-run, at most 2 rounds.** Read the disagreements for the cause and fix it at its source: the discovery query or seeds (the wrong population), the fit prompt through `/icp-prompt-builder` (the right population, wrong verdicts), or the disqualifiers (update `offer_fit_disqualifiers` in place in its one canonical home, the top-level `offer` block or the segment's entry in `offer.segments`, and log why). Then re-sample, re-classify and draw a fresh 25. Still failing after the second round means stop before any Phase B spend and report the disagreements and what was tried. That is a GO-gate condition (below), not a new pause, and it holds under `auto_execute` too.
- **Reset.** Re-sampling Phase A for any reason resets `list_qa_stage` to `none`, so a `passed` from an older sample never carries over. A profile with no `list_qa_stage` field reads as `none`, and the QA never reopens a TAM that reached `full_enriched` before this check existed: it runs on that client's next Phase A. At the GO gate, `none` means the QA has not run yet, so run it before deciding (it is part of Phase A); `none` is never a stop by itself.
- **Under `review_gates`**, the operator sees the 25 rows (both verdicts and the reasons) at the GO gate.

### The GO gate and Phase B

**Context sweep check at the GO gate (added 2026-09-24).** Before Phase B, read the top-level `context_sweep:` block in `client-profile.yaml` (protocol: `client-context-sweep.md`). Retry any core source (Slack channels, Slack DMs, email, Drive) still `blocked`, and confirm every blocklist the sweep found is in `profiles/<business-slug>/suppression-list.csv` with its company domains resolved, so `/lead-scoring` drops those companies before any email spend. A missing block runs the sweep now. A source still blocked after the retry, or a blocklisted name still without a domain (`unresolved_blocklist_names` above zero), is a flag in the GO gate report, not a stop here, and it never holds research or the build. The one hard stop sits at upload (`/cold-email-kickoff` Step 6, before the draft upload), and only the operator can waive a source (`waived_by_operator`), never Claude.

**GO gate (auto-approves within ceiling under `auto_execute`; otherwise a manual stop).** Scaling the sample to the full universe is BOTH a strategy decision ("whole universe now, or launch on a slice first?") AND a spend decision (full-universe enrichment is real money), so it stays a gate. But under `run_state.execution_mode = auto_execute` the operator has already chosen "proceed and pick the strongest option," and the strongest default under the high-volume doctrine IS the whole universe, so do not serialize the common case on a click. **Auto-approve Phase B (report it, do not stop) when ALL of these hold:** (1) the previewed full-universe enrichment cost is at or below the remaining `run_state.spend_ceiling_usd` (a real number greater than 0), (2) no slice-first / partial-build instruction is on record for this client, (3) discovery converged on one offer-fit population (one vertical when the offer is vertical) at the Phase A fit target (Aaron process alignment, operator directive 2026-09-22; supersedes "converged on one vertical"), and (4) the 25-account list QA is recorded as passed (`run_state.status.list_qa_stage: passed`). On auto-approval, report it like any within-ceiling spend ("GO gate auto-approved: full-universe enrich ~$X within $Y ceiling; N survivors") and continue to Phase B. **STOP for the operator's explicit "build the full TAM" when ANY of these hold:** the previewed cost exceeds the ceiling, `spend_ceiling_usd` is a 0 the operator set on purpose (a null, unset, or old-default 0 is first rewritten to the standing 100, per `/autonomous-execution-policy` section 2), the operator asked to launch on a slice first, the 25-account list QA is still failing after its two fix rounds (`list_qa_stage: failed`), or the mode is `review_gates`. This keeps the human stop where it earns its keep (a real spend fork or a deliberate slice-first launch) without pausing every hands-free run. The over-ceiling stop is the same fork the Phase B Collection scope rule describes below, whose first remedy is trimming signal columns, never companies or contacts, so the two never disagree. **Division of labor.** Seat A (this Claude Code) always does discovery (full source-native capture) and the ICP-fit decision (cheap classify by Claude Code sub-agents over the discovery source's already-returned text plus any free homepage text; a web crawl escalates only the ambiguous rows, then Claude judges good/maybe/bad). Beyond discovery and fit, **by default (`seat_a`) Seat A does ALL the enrichment hands-free: source-native first, then every beyond-source column via its own tools.** Claude pulls what the company-data provider returns (its company-search rows already carry the firmographics; where the provider exposes a bulk-domains mode, use it for a known-domain set) and what the company-discovery source's own native enrichers return, then collects the beyond-source columns (web crawl, paid-scraper ads, org-depth, web search) itself via the Layer 1b fast crawl. Record `run_state.tam_enrichment_path`: **`seat_a`** (default), where Seat A completes the entire `collect_now` set itself, source-native and beyond-source alike, with no external round-trip; **`seat_a_then_revcode`**, the operator's GO-gate choice to instead hand the beyond-source columns to the external enrichment platform named in the stack contract via the Layer 1c copy-paste handoff (a blocking round-trip they run with their own keys and integrations). This is the operator's call at the GO gate, not a forced default. Once the operator says go, discovery, fit and enrichment all run hands-free under `seat_a`; only the optional external leg blocks.

**Phase B: full pull, then judge and enrich the wave, then `tam_stage: full_enriched`.** Pull the **whole market** inside the budget, qualify the **wave's scope** cheap (Layer 1a, drop only `bad`), then capture the default set and discover contacts on every survivor, collecting the catalog's conditional signal columns alongside where the catalog marks them `collect_now`:
- **Seat A: pull + judge the wave (always).** Capture the full source-native field set on the whole pull, run the fit decision on the wave's scope (the parallel Claude sub-agent fit pass of Layer 1a step 4 over the source's returned text plus free homepage text; a web crawl only to escalate ambiguous rows), and apply the fit gate. Hands-free.
- **Enrich on `enriched` survivors.** Claude pulls the source-native columns (the company-data provider first, then the company-discovery source's native enrichers, Layer 1b). For every column needing a tool beyond those two, generate the copy-paste external handoff prompt (**Layer 1c** below), present it for the operator to run, then **BLOCK and wait for the returned enriched CSV** and join it onto `tam.csv` by `company_domain` (while blocked, do NOT scrape those columns yourself). The block holds `full_enriched`, and so campaigns, only while a default-set column is still out: a conditional signal column never holds the flag (Collection scope rule below), so when only signal columns are still out, set the flag once the default set and contacts are in, and join the signals when they return, which triggers `/lead-scoring`'s rescore.
- **Seat A: derive + write (always).** Derive the free columns and write `tam.csv`.

"Full qualified universe" means every ICP-fit survivor mapped (so you never hunt for more companies again), NOT every raw discovered domain. Judgment covers the wave's scope (the whole pull for the whole-TAM first wave), and each later wave judges its own scope from the same pull. Keep the cheap-qualify-before-enrich gate below: discover broadly, drop `bad` fit cheaply, pay to enrich only survivors. Set `tam_stage: full_enriched` ONLY once the full survivor set is fit-scored with its default set captured and its contacts discovered (whichever path). A build that collected zero paid signal columns reaches `full_enriched` legitimately; a signal column filled later triggers `/lead-scoring`'s rescore, the same way the Monthly Refresh does.

**Collection scope on survivors: conditional signals (Aaron process alignment, operator directive 2026-09-22; supersedes the 2026-06-29 "Signal collection is a MUST" HARD RULE, reversal approved by the operator 2026-09-22).** Every good-fit survivor gets the default set the catalog defines: firmographics, the fit and offer-relevance fields, every free Layer-1 field that comes with the rows, the derived columns, the per-contact copy variables (`sells_to_vertical`, `service_offered`, and the optional `own_best_client` when a locked offer or its copy uses it), and its contacts (Layer 1d). A paid why-now or intent signal is collected only where the catalog marks it `collect_now` under its offer-need test (the offer cannot find its buyers from firmographics, or a live test needs it); the rest stay `in_reserve` as "not needed, offer-led" (Aaron, Sep 14: "you don't need intent data to know that a business with an Instagram account might want more reach on Instagram"). This applies to the **Phase B full build** (NOT the Phase A sample, which stays bounded so the GO gate still means something). **Over the ceiling, trim signals first, never companies or contacts:** if the previewed cost exceeds `run_state.spend_ceiling_usd`, cut the conditional signal columns first (lowest value per dollar first, `worth_a_fight` last) and report each cut; the budget goes to mapping the whole TAM before any signal. If the default set alone still exceeds the ceiling, stop and ask, per the standing budget rule (unchanged). (The Collection Scope rule in `/data-point-discovery` owns the principle; *launch* is `/campaign-strategy`'s layer.)

**The downstream gate (binding).** `/campaign-strategy` and `/campaign-approval-brief` MUST refuse to start unless `run_state.status.tam_stage == full_enriched` (mapped, fit-scored and contacts discovered; signal columns optional) and, when scoring is required, `run_state.status.scoring_stage == complete`. **`/lead-scoring` is optional for a first wave that ships every tier, and required when sending capacity forces a cut** (list speed rules, operator directive 2026-09-26; `/phase-3-list` step 3). A sample TAM is never enough, and neither is an unscored TAM when scoring is required. Route incomplete TAM work back here and required scoring to `/lead-scoring`.

**The GO gate may preview a low cost and still hold.** When the pull runs mostly on plan credits the preview can land near zero, but the gate still holds on its strategy half and on the 25-account list QA: a cheap Phase B is not an approved one.

## Filter-First Discovery. HARD RULE (the discovery route; operator decision 2026-09-28, formerly the Case-Study-Anchored Discovery HARD RULE)

**Build the TAM by filter by default. A lookalike is the exception, used only when the offer needs it AND the TAM is small or hard to build by filters** (operator decision 2026-09-28, a standing rule for every client). This supersedes the 2026-07-03 case-study-seeded lookalike spine and the 2026-09-22 ruling that the lookalike is a MUST. The live order is `outbound/reference/provider-routing.yaml` `layers.company_discovery` (with `route_default: filter`), which overrides any order in this prose.

**The route is set per group before any pull, and recorded.** `run_state.discovery_route` holds the client's route (`filter` | `lookalike`) with its reason; a missing field reads as `filter`. Any group that takes the lookalike route is named in `tam-build-report.md` with the evidence that met both conditions below.

**Filter route (the DEFAULT).** When filters can describe the TAM (headcount, geography, title, and industry expressed as the keyword stack), build it directly by filtering:
- **Count first, then pull.** Resolve the enums with the company-discovery source's industry, technology and location lookups (guessed enum values silently return wrong results), then read its `company_search` `totalElements` with the list's filters and keyword stack to size the first search idea before the sample. Once the keyword mining has refined the search, read GetLeads `count_contacts` on it: that exact count sizes the full export (an exact count, not a pull, at 0 credits; the export still bills plan credits for the records it returns, so it is never "free").
- **The full company export runs in GetLeads on the refined search** (`layers.company_discovery` `order`; operator directive 2026-10-06, see `standing-rulings.md` `discovery-flow`), rolled up to one row per `company_domain`. AI Ark may run the same export in parallel (`parallel_if_fast`), deduped on `company_domain`, only if its export is fast; if slow it is skipped and logged. It is a parallel source, never a gap-fill rung, and there is no thin-universe top-up step any more. In the union the first source that returned a company keeps `source`.
- **Reveal and lookup-by-person calls are never a discovery rung.** A call that returns emails or bills per revealed person (for example a decision-maker lookup that always returns emails) is a reveal, and reveals belong to `/email-waterfall` on the contacts a wave picks. Discovery calls return companies and people without revealing email.
- **The filter route runs the house order (the default; operator directive 2026-10-06, see `standing-rulings.md` `discovery-flow` and `aaron-flow.md` section 6).** For each vertical: (1) the AI Ark company sample of 200 to 300 companies with every company filter, fit scored by batched Claude sub-agents, and the keyword mining that turns it into the refined search, with every exclude guarded by `keyword_mine.py` and costed by `exclude_cost.py` before it is used (`outbound/reference/ai-ark-people-discovery.md` Step 1 and 4b, ruling `exclude-guard`; this is the Phase A sample and tuning); (2) the full company export in GetLeads on the refined search (Step 2); (3) company fit once per `company_domain`, then people in GetLeads at the `good` and `maybe` companies (Step 3, Layer 1d below); (4) the email waterfall, later and only on the launch set (Step 4, `/email-waterfall`). The superseded 2026-09-28 and 2026-10-05 AI Ark people-first route (a people search rolled up to companies, refined on a 200-row people sample) no longer runs.

**Lookalike route (the exception; BOTH conditions must hold for the group).**
1. **The offer needs it.** The buyer is defined by resemblance to specific companies, or by a trait no filter field can carry (so not headcount, geography, a title, or a keyword the company's own description would contain). Judge it from the locked offer, `offer.icp_inclusion` and the targeting spec, before any pull. When this fails, the group takes the filter route whatever its size, and a thin filter result is widened on the filter ladder below.
2. **And the TAM is small or hard to build by filters.** Small: the counts above put the whole universe low. Hard to build: the filter route's Phase A sample stays under the fit rubric's ~50% rework floor after two tuning rounds, or the 25-account list QA fails its two fix rounds because the filters cannot isolate the population (not because the fit prompt judged the right population wrongly).

The lookalike tool on this stack is untested and not in the contract (`layers.company_discovery.lookalike`), so the lookalike route also needs the operator's approval before its first call. Never substitute another tool for it (`/tool-balance-guard`).

**Proof, not mechanism: `discovery_motion` keeps its meaning.** The flag records whether client proof stands behind a row, because `/campaign-strategy` reads it as the copy-proof discriminator. `proven` = the row's `group` holds at least one real client win that fits the locked offer, with its proof in `/social-proof-bank`; `expansion` = no client case study backs the row. On the filter route every row starts as `expansion`. Rows are matched to the proof bank's groups (the sub-industry or what-they-sell clusters) by the Layer 1a step 4 Claude classify when the groups already exist, or as a no-spend re-tag pass once the bank finishes; a row whose group has an offer-fit client win is re-tagged `proven` before `/campaign-strategy` reads the column. A row is never `proven` because of the mechanism that found it.

**Grouping.** On the filter route there is one filter-built TAM per confirmed segment, and `group` is a tag on its rows (blank when no proof-bank group matches), not a separate pull. On the lookalike route each group keeps its own seed set and its own group-TAM. Record `segment`, `group` and `discovery_motion` on `tam.csv` either way.

**Existing builds are not reopened.** The rule applies at a client's next Phase A. A TAM that already reached `full_enriched`, or a Phase A sample already built on a lookalike, is never re-pulled because of it. A later refresh or widening of such a TAM uses the filter route.

**Volume: the expansion-for-volume ladder (HIGH-VOLUME DEFAULT, operator directive 2026-07-07).** A TAM's natural saturation is **a trigger to WIDEN, not a ceiling.** The target is 1,000 to 20,000 leads per campaign, and most of that comes from **contacts per company** (Layer 1d pulls every ICP-matching decision-maker on every company, every title in `offer.title_stack`, per the 2026-07-12 scrape-all directive). When a TAM still needs more *companies* to hit its campaign's volume, widen in this order, **re-checking ICP fit at every rung** (fit drops as you widen, by design, so this is the calibrated gate below, NOT a re-clear of 80%):
- **Filter route:** (1) more keyword variants in the stack, from `industries_in`, the locked offer and `offer.icp_inclusion`; (2) more markets and geographies the client can serve; (3) wider headcount bands where the offer still lands; (4) merge sibling segments that share a buyer and a message into one big campaign; (5) re-run the AI Ark company sample and keyword mining on the widened definition, then the GetLeads export on the new refined search (operator directive 2026-10-06, see `standing-rulings.md` `discovery-flow`; the old thin-universe top-up is gone).
- **Lookalike route:** (1) more or stronger seeds, 5 to 10 offer-fit companies (within the tool's seed cap and the AI-5/client-5 balance), promoting validated-`yes` companies into the seed set; (2) loosen similarity toward the tool's mid band, paging under an exclusion list so only net-new rows are billed; (3) more markets and geographies; (4) wider headcount bands; (5) merge sibling group-TAMs; (6) a filter top-up (Layer 1a step 1, with the keyword stack and `industries_out` exclusions), its rows tagged by proof like any other.

**The fit gate, anchored correctly ("when it makes sense only").** 80%+ is the TUNING target for the tight core (the first filter pull, or the seeded core on the lookalike route): tune it before scaling. It is NOT the widening stop. Widening deliberately reaches less-similar but still relevant companies, so fit drops there by design, and that is allowed. Keep widening while the pull stays on-ICP down to the validation rubric's ~50% REWORK floor. **STOP when fit hits the ~50% rework floor (you are pulling noise) OR the campaign's volume target is reached, whichever comes first.** Never a blanket 80%, never merely a count. Volume pulled *below* the rework floor is bounce risk, not volume. The full ladder and its capacity math belong with the high-volume doctrine this workspace records.

**Sequencing.** On the filter route this skill never waits on `/social-proof-bank`: the bank runs alongside it, and its groups feed the `proven` re-tag above. On the lookalike route the group's seed set must exist first. Proof-facts never hold a build on either route (operator directive 2026-09-22). See `/phase-3-list`.

### When the lookalike route runs (the exception's mechanics)

These apply only to a group that met both conditions above.
- **Seeds = the 5 to 10 companies that best fit the LOCKED offer** (Aaron process alignment, operator directive 2026-09-22): the client's own case-study and customer companies that fit this offer first (Aaron, Jun 22: "focus on the companies I've already gotten results for"), topped up with researched offer-fit exemplar companies when the client has fewer (a flagged aspirational exemplar is already a valid seed, per `/social-proof-bank`). When the locked test set holds several offers, pick seeds that fit the whole set (for per-buyer-type clients, that segment's set in `offer.segments`): each offer runs only in the first-wave list segments its own fit filters pass, and offers are compared only on the ground they share (fit-matched placement, operator decision 2026-09-23). A group led by the client's offer-fit wins is `proven`; a group seeded only from exemplars is `expansion`, with offer-led copy and no client-specific proof. If no credible offer-fit exemplar can be found, say so in the build report and build the group on the filter route.
- **Pull.** Tune the similarity threshold on the Phase A sample (Phase A above), and promote validated-`yes` companies to seeds as you tune. A seeded lookalike is the high-precision mode (~68% true-ICP versus ~39% for a raw category pull, measured on a past client TAM).
- **SEED vs PROOF (two gates, do not conflate).** The case-study *company* seeds the lookalike (a case study, a happy customer, or a flagged exemplar). The case-study *facts* (exact number, timeframe, referenceable client) are the proof the copy will later need, and `/social-proof-bank` confirms them at seed time. Missing facts are collected (`/proof-asset-request`) in parallel with the build: **the seeds gate the lookalike build; missing proof-facts never hold it** (operator directive 2026-09-22). They gate only copy that names or quantifies the case study.

## The Cost Model (the "right order and way")

### Layer 1a: qualify up front (cheap, company-level)

> **Phase scope (per the HARD RULE):** in **Phase A** this qualify pass runs across the bounded **sample**; in **Phase B** it runs across **the scope of the wave being built** (the pull itself covers the whole market; for the whole-TAM first wave the scope is the whole pull). "Across the whole scope, cheaply, before enriching" is the principle *within whichever phase you are in*. It is NOT a licence to discover and qualify the entire universe during Phase A (that would moot the sample-first GO gate), nor to judge companies outside the wave's scope in Phase B.

Cost here is flat or per-page, not per-contact-credit, so qualifying every company in the current phase's set is affordable. This sub-layer ends at a **fit gate**; only survivors reach the expensive Layer 1b.

1. **Discover the company universe on the route the Filter-First Discovery HARD RULE above sets (not a free operator pick), in the `provider-routing.yaml` `layers.company_discovery` order.** **Filter route (DEFAULT), the house order (operator directive 2026-10-06, see `standing-rulings.md` `discovery-flow`; `ai-ark-people-discovery.md` Steps 1 and 2):** resolve the enums, size the first search idea with the company-discovery source's `company_search` `totalElements`, pull the 200 to 300 company sample with `company_search` (filtering on company size, HQ location, industry, technology, plus the keyword stack), score its fit and mine every include and exclude keyword into the refined search, then size the refined search with GetLeads `count_contacts` and export the whole company list in GetLeads, rolled up to one row per `company_domain`. AI Ark runs the same export in parallel only if fast, deduped on `company_domain`, never as a gap-fill rung. **Lookalike route (the exception, only when the offer needs it AND the TAM is small or hard to build, with the operator's approval of the untested tool):** a lookalike seeded from the group's 5 to 10 best offer-fit companies (its offer-fit case-study/customer company websites first, from `/social-proof-bank`, topped up with researched exemplars). **Reveal and lookup-by-person calls are never a discovery rung.** **Everything else is extension/augmentation, not the primary list:** WebSearch (SERP/URL discovery to *augment* coverage), maps/local scrapers (a truly local-SMB / maps-first universe is its own motion), and vertical revenue databases layer on top of the discovery route, never replace it. Discovery is the company list, not contacts. **HARD RULE (cost): every discover/count call carries the list's employee-size range, location and hard filters, and no lookalike is over-pulled.** The list's filters are the intake `icp_hard_filters` from `client-profile.yaml` as widened or narrowed by the locked offer's `offer.icp_inclusion` (read from `offer.segments[<segment>]` when the client has per-buyer-type offer sets), never the intake form's hard filters alone (the intake ICP is a starting point, not a ceiling; operator decision 2026-09-23, Aaron pre-launch gap audit). Apply that filter set to the discovery query, never a hardcoded range: read `headcount_buckets_in` / `headcount_min/max`, `countries` / `states`, `revenue_min_usd`, the `offer.icp_inclusion` filters, and `industries_out` (passed as exclusions), and pass them as the discovery filters (on the lookalike too, not just filter-only queries) so you never pay to pull out-of-ICP rows. **The intake ICP is the starting point, not the ceiling, and industry taxonomy filters give way to a keyword stack (Aaron process alignment, operator directive 2026-09-22; Aaron, Apr 13: "we scrap the industry filters altogether. You can essentially just use AI to generate the exact keyword variations based on your ICP and stack those").** Industries-in never go on the pull as a provider industry-taxonomy filter. At the start of Layer 1a, Claude Code generates the keyword stack in the session (every keyword variation of the plain-language `industries_in`, the locked offer, and any keyword entries `offer.icp_inclusion` carries; never an AI column in the list workbench), passes it wherever the discovery tool takes text (a phrase-match, keyword or natural-language ICP field), and records the exact stack in `tam-build-report.md`; the Claude Code fit classify (steps 3-4) does the rest. `industries_out` stays a named exclusion list, mapped onto a tool's exclusion values only where the tool needs them. **Read `offer.icp_inclusion` with the same three-case discipline as `offer_fit_disqualifiers` (step 3):** a populated field is authoritative; an explicit empty `[]` is a real answer (the offer adds no inclusion filter); an absent (or `null`) field means offer lock never wrote it, so derive it here from the locked offer and say so in the build report. And never overpull a finite pull on either route: count first (an exact count, not a pull), take one clean pull, and guard any follow-up pull with a server-side exclusion list so duplicates are never re-billed. **Filter caveat to verify on whichever tool fills the slot:** employee-size filters are frequently **bucket-based and include any OVERLAPPING bucket**, so a request for 100-2000 can return a whole 51-200 bucket (down to 51) AND a whole 1001-5000 bucket (up to 5,000). So (a) set the range to the exact size buckets of that filter set (`headcount_buckets_in` as widened or narrowed by `offer.icp_inclusion`), and (b) **post-filter returned rows by their `headcount` bucket to that size set**, because a per-record-billed source still charges for any overlapping-bucket row it returns (choosing buckets deliberately is the real cost lever). Lookalike (domain-seed) mode normally applies the same firmographic filters at the same bucket granularity, not looser: verify this on the chosen tool rather than assuming it. A raw category pull is also noisy (category taxonomies routinely file vendors, SaaS and adjacent suppliers under the vertical, e.g. ~39% true-ICP on a broad vertical category), which is one more reason the pull carries the keyword stack rather than a category filter, and why the ICP-fit pass (steps 3-4) is what removes the off-ICP rows. **Read the chosen discovery source's own capability map, model routing and plan gates before routing a discovery/research job there**, and confirm which filters its current plan actually unlocks: tech-stack/vendor filters, query inclusion/exclusion, AI segmentation and bulk name-matching are commonly gated to higher tiers. Never route a discovery filter through a tool whose plan does not expose it; get that signal another way.
   **Post-provider account QA, on every source (added 2026-09-24; `list-production-standard.md` section 5).** A filter sent to a provider is a first pass, never the final check, for the discovery source and for every other source that adds companies (the GetLeads full export, the optional AI Ark parallel export, any widening rung). After each company pull:
   - **Check the headcount distribution.** Bucket the rows by the targeting spec's `expectations.headcount_bands` and compare them to `account.headcount`. A share outside the range above `expectations.max_share_out_of_headcount_range` is a CRITICAL provider-filter anomaly. The offending rows are gated out before any enrichment spend, never deleted: `fit_status: bad`, a `fit_reason` naming the out-of-range headcount (or geography), and `enrichment_tier = qualified_out`, so they stay in `tam.csv` and the survival ledger counts them under `dropped_icp_fit`. The anomaly, with the source that produced it, goes at the top of `tam-build-report.md`, directly after the sub-floor alarm when that fires. Example: requested 20 to 499, and 48% of rows are under 20.
   - **Do the same for geography**, against `expectations.max_share_out_of_geography`.
   - **Escalate only uncertainty, and only in the wave's scope.** A headcount at a company in the scope of the wave being built that is missing, borderline (within `borderline_pct` of a bound), or conflicting between two sources gets at most one cross-check, through `provider-routing.yaml` `layers.headcount_crosscheck`. A confident in-range count is never re-bought.
   - **Keep the raw value and its `headcount_source`** next to the band.

   Headcount here is usually a count of employee profiles or a size band. It under-counts field-heavy businesses, so borderline is judged generously and never auto-dropped.
2. **Capture the discovery tool's FULL native field set on every company (source-native full capture).** The discovery response already holds far more than a few firmographics, and everything in it is **free beyond the per-record search credit already spent**, so write EVERY field the tool returns to `tam.csv`, never a cherry-picked handful (the failure that produced a domain + name + score-only list). A company-search response typically returns, in one payload: identity (name, domain, LinkedIn, provider id), firmographics (company type, ownership status, company size, HQ location, industries, SIC/NAICS, revenue, funding round/amount/date, IPO/acquired dates), web-traffic (monthly visits, global/country/category rank, bounce rate, pages-per-visit, visit duration, top topics), sales-motion signals (pricing available, demo available, free trial available, documentation exists, downloadable, mobile apps exist, online reviews exist), tech (technologies used), and hiring (job posting title / seniority / type / location). A lookalike discover response typically returns domain, company name, industry, headcount, headcount range, location country / state / city, LinkedIn URL, description, and a similarity score. Map these onto the STABLE CORE canonical names and keep every remaining field as a **source-native extension column** (verbatim source name and value). Do NOT trim to a catalog subset: the catalog governs data points BEYOND the source response, not the source's own free payload. A company-search source is typically metered **per record returned**, so a whole-TAM pull is per-company spend. Estimate `records x per-record` via `/api-cost-governance` (the fields are free; the records are not).
3. **Free disqualifier pre-screen (firmographic AND offer-derived), then a cheap fit classification from data the discovery source ALREADY returned, not a fresh crawl.** First drop any company that fails a hard firmographic/discovery-snippet disqualifier; that costs nothing. Then drop the companies the offer itself rules out, also for nothing, and only then qualify what is left.

   **The offer-derived disqualifier list (free, and it runs BEFORE any paid classification).** Some companies are unsellable for a reason the ICP cannot see: they cannot use the thing this offer delivers. Screening them here, in the free pre-screen, is strictly cheaper than paying a classify credit and then an enrichment credit to discover the same thing later. **Build the list from the LOCKED offer set** (per segment, operator decision 2026-09-22: a company is auto-DQ'd only when every offer in its segment's set disqualifies it, the intersection of their `offer_fit_disqualifiers`) at the start of Layer 1a: read `offer.lead_magnet` plus its detail fields (`offer.lead_magnet_details`, `offer.lead_magnet_cta_direction`, `offer.lead_magnet_gap`) from `client-profile.yaml`, and the selected magnet's write-up in `lead-magnets.md`. **The list has one canonical home: `offer.offer_fit_disqualifiers` in `client-profile.yaml`, written by `/lead-magnet-brainstorm` at offer lock.** Read it from there. The three cases are distinct and must not be collapsed: a populated list is authoritative, so use it as written and do not re-derive alongside it (two lists silently drift, and the pre-screen would start dropping companies the offer work never sanctioned); an explicitly empty `offer_fit_disqualifiers: []` is a real answer meaning this offer excludes no company type, so the gate runs and drops nobody; the field being **absent** means offer lock never wrote it, so derive the list here and say so in the build report, because a silently self-derived list is the drift this join exists to prevent. Each entry answers one question, the same question the `offer_fit` judgement in step 4 asks: **can this business actually use, stock, deploy, or buy the thing the offer delivers?** The recurring categories, to be instantiated against this client's actual offer rather than copied verbatim:
   - **Already has its own version of this** (the canonical one). A private-label manufacturing offer excludes the clinics that already own a supplement brand: they are the offer's competitor, not its buyer.
   - **Franchise or head-office-controlled entities that cannot decide locally.** The local site cannot buy, and the entity that can is not the row you discovered.
   - **No physical or operational capability to use the deliverable.** No premises, no fleet, no lab, no team, no license: whatever the offer structurally requires.
   - **The client's existing customers.** Already sold; route them to the client, never to a cold campaign.

   **Matching discipline for an auto-DQ is NAME + DOMAIN only, exactly as strict as the `hard_no` rule below, and it is not to be loosened.** Keyword and specialty matching over-DQs real ICP accounts at a rate this repo has already measured (290 false positives versus 23 true name/domain hits, verified 2026-06-13). So an offer disqualifier auto-DQs only when it is decidable from the company's name and domain. **Anything that needs a judgement call is NOT an auto-DQ:** it drops through to the `offer_fit` classification in step 4, where the Tier-1 and Tier-2 machinery already exists to settle it. The free pre-screen takes the certain cases; the classify pass takes the rest. **What an offer auto-DQ must write:** `offer_fit = no` plus a one-line `offer_fit_reason` naming the disqualifier, and `fit_status: bad` with the matching `fit_reason`, then `enrichment_tier = qualified_out` (the same treatment `hard_no` gets below, and the row is never deleted). Skip those values and the survival ledger cannot count the row under `dropped_offer_fit`, so the reconciliation breaks on exactly the rows this pre-screen removed.

   **Then qualify every company that survived both pre-screens, in two tiers, cheapest-first.** **The discovery source has already crawled these sites and returns their text on either route (its company `description` and keyword fields on the filter route; the similarity source's text on the lookalike route), so re-running a web crawl plus a web search to re-derive "what does this company do" on every company is redundant work: removed.** The fit *gate* stays (it is what removes off-ICP rows and stops you paying per-record enrichment on them); only its *mechanism* changes:
   - **Step 0 of the tiers: Spider homepage first, on every surviving company (LOCKED DEFAULT, operator directive 2026-10-12, mirrors the A-Sales GTM folder).** Company fit is read from the company's own homepage, together with the discovery text and data fields below, not from the discovery text alone. Run on the COMPANY file (one row per `company_domain`, never the contacts file): `node outbound/scripts/research/spider_fit_fetch.mjs fetch --input <company csv> --out-dir <run dir>`. It does one Spider Cloud fetch per company, cached per domain, cuts it to 3,500 characters, and flags thin, parked and redirected sites in code (under 500 characters of text, a for-sale page, or a redirect to another domain). **Before any spend it reads the live Spider balance and estimates the run (uncached homepages x 8 credits, a planning figure from A-Sales; the first FNNL run measures the true cost into `manifest.json`): if the balance is short or unreadable it stops with exit 3 and nothing is spent. Say so plainly, ask Luke to top up, then rerun the same command; it resumes from the cache. There is no per-run credit cap and no substitute fetcher.** Use `--dry-run` first to show the estimate. A source that already returned website text can pass `--site-text-field` and skip Spider for those rows. Spider is never a source of companies, contacts or emails. Then `spider_fit_fetch.mjs batch` writes judge-ready files of 300 companies (data fields, site status, homepage text), batched Claude sub-agents judge them (about 10 at once, one output CSV each, columns `company_domain, fit_status, fit_confidence, fit_reason, offer_fit, offer_fit_reason`, plus any variable the client prompt defines), and `spider_fit_fetch.mjs merge` joins them by `company_domain` with an id and count check and applies the `offer_fit = no` to `bad` rule in code. A company left with no valid verdict counts as dropped and is reported at the top of the run summary; re-run `batch --only-ids` on the missing ones. **Gate each client's first run with a 20-row agreement check** (Luke or a prior answer as gold, `merge --gold`): keep/drop agreement must hold before the full list is judged. A site flagged thin, parked or redirected is judged on the discovery text alone and is held, never dropped for being unreadable. The same cached homepage text is what personalization research reads for the company's offer, customers and wording (see `/personalization-subagent-pattern`); do not fetch it a second time.
   - **Tier 1: cheap classify on already-returned text, every surviving row.** Score fit from what discovery already paid for, now read together with the Spider homepage text from step 0: the source's `description` plus industry/industry-group, business model and keyword fields (treat a similarity score as a relevance *prior*, NOT a fit verdict; verified ~68% true-ICP on lookalike and ~39% on category, which is exactly why a fit pass still runs), and for filter-sourced rows its returned fields, top topics and sales-motion booleans. Where the discovery source offers **free homepage text extraction for a domain just discovered this cycle**, it may stand in for the Spider fetch on those rows via `--site-text-field`. **Claude Code sub-agents classify this in disjoint batches** (per `/personalization-subagent-pattern` and `/ai-model-routing`: each sub-agent reads its own slice of the on-disk text and writes its own output file, merged by `company_domain`). At sample scale a discovery tool's own native ICP-fit validator can be a convenient alternative, but those flood context past a few hundred rows, so the sub-agent fan-out is the full-TAM workhorse. **This same pass emits the `offer_fit` judgement (step 4), on the same text, for no extra credit.**
   - **Tier 2: escalate ONLY the ambiguous rows to a deeper crawl.** When Tier 1 returns low `fit_confidence`, a borderline `maybe`, or an `offer_fit = unclear` that deeper pages could resolve, THEN run a multi-page Spider read on just those rows (`spider_fit_fetch.mjs fetch --pages 3` on a file holding only the ambiguous companies, which passes the same balance check; pricing, `/customers`, `/about`), compress with a Claude Code sub-agent, and re-score. This bounds the crawl to the minority of companies whose fit is not decidable from the homepage plus returned text, instead of crawling everyone. **An `offer_fit` still `unclear` after escalation survives on the ICP verdict. It is never resolved to `no` by default**, because a default-to-drop ambiguity bucket is exactly how a launch slice starves.
   - **A missing attribute is held and re-read, never dropped (ruling `attribute-reread`, operator 2026-10-12).** When a campaign needs an attribute the returned text does not state (an agency's client type, for example), the company stays `maybe` with the attribute blank, in every list mode, `volume` included. The Spider homepage text from step 0 is read first; the free site re-read below is the fallback for rows Spider could not read (thin, parked, redirect, error) or whose attribute sits on a page other than the homepage: `outbound/scripts/site_reread.py` `fetch`, then `batch` (a few hundred sites per file), batched Claude sub-agents (about 10 at once) against a per-client rules file, then `merge` with its count check. Aaron's ~40% attribute floor is measured after the merge (`ai-ark-people-discovery.md` Step 2.5).
   This is the `gate_role = qualify` work, now sourced from the discovery payload plus free homepage text first, with the crawl reserved for escalation. The `gate_role = enrich` data points come later, on survivors only (Layer 1b: Seat A via its own tools by default, or the external round-trip under `seat_a_then_revcode`).

> **Why classify, not re-crawl (and why the gate still exists).** A lookalike tool's automatic similarity score is *relevance-to-seeds*, not a good/bad ICP verdict: verified on a client TAM at ~68% true-ICP (best lookalike) and ~39% (category). So the fit **gate** stays, because it removes that off-ICP slice AND prevents per-record enrichment spend on it. But the external crawl that used to run on **every** company is removed, because the discovery source already crawled the site and hands back the text. Net: the costly per-page crawl drops to the ambiguous minority, the classify runs in Claude Code sub-agents with no per-row AI spend, and the list stays clean.
4. **Score fit (good / maybe / bad): TWO judgements on ONE pass, ICP fit AND offer fit. Claude's decision.** Run the fit filter (the `/icp-prompt-builder` prompt, tuned on a ~40-row mixed sample of THIS TAM's cheap layer: the source-native fields plus the free returned text/homepage from step 3's Tier 1, plus the escalation crawl on the ambiguous rows, to convergence) across the scope being judged (the Phase A sample; in Phase B the scope of the wave being built, which for the whole-TAM first wave is every pulled company) on a **parallel batch path, never a serial row-by-row loop in the main conversation** (the no-serial-independent-work default in `/autonomous-execution-policy` section 9). Claude Code Task sub-agents fanned out over disjoint slices are that parallel path, for the bulk and for edge cases alike (per `/personalization-subagent-pattern`: one output file per agent, a count and format check on each file, a resume that re-runs only the missing or malformed slices, merged by `company_domain`, then a post-merge uniqueness check). **Two passes (list speed rules, operator directive 2026-09-26).** Pass A classifies every row in scope, and its `good` and `bad` verdicts are final. Pass B re-judges only Pass A's `maybe` rows with a tighter maybe-versus-bad line, and never re-scores the `good` rows. Never an AI API and never a third-party model: the sub-agents are Claude Code's own. Claude makes the good/maybe/bad call; write `fit_status` (`good`|`maybe`|`bad`), `fit_confidence` (0-1), and a one-sentence `fit_reason`. This is the "review good-fit / bad-fit" gate the note calls for, made cheap and automatic instead of a manual review of hundreds of rows.

   **The `offer_fit` judgement, evaluated against the LOCKED offer on the SAME classify pass (HARD survival gate).** ICP fit answers "is this the kind of company the client sells to." It does not answer the question that actually decides whether there is a sale here: **can this business actually use, stock, deploy, or buy the thing the offer delivers?** A company can sit dead centre of the ICP and still be unsellable this wave because the offer has nothing it can take. So the classify pass makes a second, independent call on every surviving row.
   - **What it reads.** The locked offer set for the row's `segment` (operator decision 2026-09-22): `offer.segments[<segment>]` when the client has per-buyer-type offer sets, otherwise the top-level `offer` block. Judge the row against every offer in that set (the primary and its validation arms): `offer_fit = yes` when any of them can serve the company, `no` only when none can, with the fitting offer named in `offer_fit_reason`. For each offer, read its `lead_magnet` plus its detail fields (`offer.lead_magnet_details`, `offer.lead_magnet_cta_direction`, `offer.lead_magnet_gap`) in `client-profile.yaml`, and the selected magnet's write-up in `lead-magnets.md`. Judge it against the same free text Tier 1 already has in hand (the discovery source's description, keywords and business-model fields, plus the free homepage text), so this is a second question on an existing pass: **no extra crawl, no extra credit, no new tool.**
   - **What it writes.** `offer_fit` (`yes`|`no`|`unclear`) and a one-sentence `offer_fit_reason`, on every row. Like `hard_no` below, this is a first-class machine-checkable column rather than a buried note, because the gate report has to count it.
   - **How it resolves.** `offer_fit = no` resolves the row to `fit_status: bad`, and it is dropped before Layer 1b enrichment spend. **`unclear` NEVER drops a row on its own:** route it through the same Tier-2 escalation that low `fit_confidence` rows already use, and if the deeper pages still cannot settle it, the row survives on whatever the ICP verdict says. An ambiguity bucket that quietly resolved to "drop" would itself be the starvation mechanism the reporting guard below exists to catch, and it would contradict this skill's conservative default of gating only what is clearly `bad`.
   - **HARD precondition: no locked offer, no offer-fit gate.** This judgement is unanswerable without an offer, so it is not optional and it has no fallback. If the row's segment has no locked set and the top-level `offer.lead_magnet` is missing or empty, STOP and route back to the offer work (see Stop Gates). **Never silently score ICP-only and continue:** that spends Layer 1b enrichment money on companies the offer cannot serve, which is the exact leak this gate closes. `offer.lead_magnet: direct_offer` IS a locked offer (the offer-first play that carries a direct CTA instead of a separate magnet): apply the gate question to the underlying service that CTA sells.

   **Binding meaning: `bad` now has TWO causes, and either one drops the row before Layer 1b enrichment spend.**
   1. **Outside-market by ICP.** A genuinely outside-market company, wrong entity, or no plausible customer relationship.
   2. **Cannot use the offer (`offer_fit = no`).** The business cannot use, stock, deploy, or buy what the locked offer delivers, so there is nothing to sell it this wave even where the firmographics look right.

   Adjacent industries, serviceable sizes, expansion geographies, and other real but imperfect prospects remain `maybe` under both causes, and an `unclear` offer-fit read never drops a row by itself. This is an enrichment-spend gate, not the final 10-point priority score. **Record which cause fired in `fit_reason` and keep `offer_fit` on the row**, because the gate report below has to count the two causes separately and cannot reconstruct them afterwards from a merged verdict.

**Free ride-along on the same classify pass: the `sold_to` axis (who the company sells to).** The Tier-1 on-disk classify already holds the text needed to read the company's *own* customers (the discovery source's description, keywords and business-model fields, the company-data provider's company description, and the free homepage text). Emit the `sold_to` group in the **same** pass, for free: `sells_to_vertical` (text, their end-customer vertical in their own words), `sells_to_customer_size` (enum), `sells_to_department` (enum), `sells_to_motion` (enum). The same pass emits the per-contact copy variable `service_offered` (the prospect's own product or service as a short phrase; Aaron, Sep 21, variable two; `/data-point-discovery` sold-to section, Aaron process alignment, operator directive 2026-09-22), with `service_offered_source` holding the URL of the page its text came from. These are `fill_method = derived` (a classification, like `sales_motion`), `gate_role = n/a`, no per-company credit and no new crawl. Coverage is honestly `med` (many B2B firms state who they serve; some only imply it). The optional `own_best_client` (the prospect's own best client named on its own site, the deliverable's target) is NOT part of this derived pass: it is a scraped `enrich` column collected only when a locked offer or its copy uses it (a WebFetch read of the prospect's case-study or customer page, then a Claude Code sub-agent extraction, or read with no new fetch from `named_customers` or the captured homepage text where they already name one), with `own_best_client_source` holding that page's URL, `coverage = low`, and a blank never guessed. Neither is ever filled by an AI column in the list workbench. The sold-to columns join onto contacts as `co_sells_to_*` in Layer 1d and are the **highest-leverage message-differential axis** `/campaign-strategy` slices on (the "list is the message" doctrine); `service_offered` and `own_best_client` join the same way, as `co_service_offered` and `co_own_best_client` with their `_source` columns. Because the inputs are the qualify-layer text, the derived columns are available even on the Phase A sample.

#### The fit gate (between Layer 1a and 1b)

**Hard-no categories: auto-DQ plus a `hard_no` column (before the good/maybe/bad gate).** If the client profile lists `icp_hard_filters.hard_no_categories` (or `industries_out`), emit a **`hard_no` column** on `tam.csv` (the category name, e.g. `dental`/`veterinary`, or blank) and treat any non-blank `hard_no` as an automatic DQ: set `enrichment_tier = qualified_out`, and **every campaign slice MUST exclude `hard_no != ""`** so these never reach the client's reps. **Match on NAME + DOMAIN only**, never keywords/specialties (a multi-service health system that merely *offers* a dental or vet clinic is NOT a dental/vet practice; matching its keyword blob over-DQs real ICP accounts, verified on a client build 2026-06-13, where a keyword scan flagged 290 false positives vs 23 true name/domain hits). Why this matters: discovery sources mislabel adjacent verticals into the ICP (a broad `HEALTHCARE` category explicitly includes dental practices; veterinary leaks in via lookalike), and a hard-no that reaches the client's AEs is a delivery miss that does not count. This is the client-requested "hard-no scoring column": keep it as a first-class, machine-checkable filter, not a buried note.

Then, on the rows that pass the hard-no filter: keep `good` and `maybe`; gate out `bad`. Set `enrichment_tier = enriched` on the survivors and `enrichment_tier = qualified_out` on the rest. **Gated-out rows stay in `tam.csv`** with their `qualify` columns and a `fit_reason`, extension columns left blank, never deleted, so a later wave or a loosened ICP can revive them (same philosophy as `in_reserve`). **On high-stakes lists, spot-check a sample of the `qualified_out` (`bad`) rows before trusting the gate:** a native discovery-source scorer is typically ~98% accurate but its rare misses are **false-negatives** (it marks `bad` a company that actually fits), so a quick crawl-plus-classify re-check of the gated-out sample recovers the few good ones it dropped. Spot-check the `bad` verdicts, not the `maybe`s. **Sample the TWO drop causes separately, because a new gate does not inherit the old gate's track record.** Draw one sample from the rows dropped on ICP fit and a second, independent sample from the rows dropped on `offer_fit = no`, and re-check each against its own question: the ICP sample against "is this the kind of company the client sells to," the offer-fit sample against "can this business actually use, stock, deploy, or buy what the offer delivers." A single merged `bad` sample hides an offer-fit gate that is mis-firing, because the ICP drops usually outnumber the offer drops and would dominate the sample. If the offer-fit sample surfaces real recoveries, the criterion is too tight: loosen it and re-run the gate before spending on enrichment, rather than accepting a thinner survivor set. Under `auto_execute`, enrich `good`+`maybe` and gate only `bad` (the conservative default; it minimizes false drops); report the good/maybe/bad counts and the estimated per-record enrichment spend the gate saved. Under `review_gates`, show the counts plus a labeled good/maybe/bad sample and let the operator confirm or move the threshold before any extension spend.

#### Gate reporting: the survival ledger (MANDATORY, do not omit)

**A hard gate can starve a launch slice silently, and that is the known failure mode of this one.** The totals stay healthy in aggregate while one segment quietly falls under the volume it needs to launch, and nobody finds out until `/campaign-strategy` cannot build a wave from it, long after the enrichment money is spent. So **the gate does not count as run until its ledger is reported.** This is the verify-before-done rule applied to the gate: the gate returning a clean number is acceptance, not proof of outcome, and the outcome that matters is whether every slice still has enough companies left to launch.

**Report this ledger per segment AND per group, every time the gate runs:**

| Field | Meaning |
|---|---|
| `companies_in` | rows entering the gate for this segment / group |
| `dropped_icp_fit` | dropped as outside-market by ICP |
| `dropped_offer_fit` | dropped on `offer_fit = no`, so they cannot use, stock, deploy, or buy what the offer delivers |
| `survivors` | rows carried into Layer 1b (`enrichment_tier = enriched`) |

Count each dropped company **once**, under the cause recorded in its `fit_reason`, so the numbers reconcile exactly: `companies_in` = `dropped_icp_fit` + `dropped_offer_fit` + `survivors`. A row failing both tests counts under offer fit. A ledger that does not reconcile means the drop cause was not recorded per row, which is a build defect to fix before enriching, not a discrepancy to explain away.

**The sub-floor alarm. If any slice lands under the ≥500-company eligibility floor, say so LOUDLY at the TOP of the report, and name the offer-fit gate as the cause.** That floor is `/campaign-strategy`'s HARD RULE (operator directive 2026-07-12), the same floor the Signal Coverage Table further down is read against, so a slice that finishes below it is not a smaller campaign, it is a campaign that cannot launch. The alarm is the **first line of `tam-build-report.md`, above the counts table**, written in plain words ("WARNING: the <segment> slice has 340 survivors, under the ≥500-company floor. The offer-fit gate dropped 620 of 960 companies"). Never a footnote, never a cell in the ledger table, never left to the reader to notice by comparing two numbers. **A slice must never be allowed to starve quietly.**

**When the alarm fires, name the two real remedies and recommend one.** Per this skill's Material Decision Rule, do not silently accept a starved slice and do not silently widen to fix it. Under `auto_execute` (the new-client default since 2026-09-24) that means doing it in the open rather than stopping: apply remedy 1 without asking (it is free and reversible), then remedy 2 inside the budget if the slice is still short, and report both at the next checkpoint; a slice still under the floor after both goes to that checkpoint as a finding while the other slices go ahead. The remedies:

1. **Relax the offer-fit criterion.** Loosen what counts as `offer_fit = no`, push the borderline cases back to `unclear` (which survives), and re-run the gate. **Recommended first**, because the gate is a classification over text already on disk: re-running it is free and fully reversible, and a gate tuned slightly too tight is the more common cause of a starved slice than a genuinely dead market.
2. **Widen the segment.** Climb the expansion-for-volume ladder above for the group's route (on the filter route: more keyword variants, more geographies, wider headcount bands, merge sibling segments, then a fresh sample, keyword mining and GetLeads export on the widened definition; on the lookalike route: more or stronger seeds, looser similarity, then the same widening steps and a filter top-up) to bring more companies into the gate. Weaker as a first move because it costs real discovery spend and it cannot help at all when the offer-fit gate, not the company count, is what emptied the slice. Reach for it once remedy 1 has been tried and the survivor count is still short.

If neither clears the floor, report that honestly: this segment does not support a launchable campaign for this offer. That is a real finding the operator needs, and it is a far better outcome than a sub-floor campaign built quietly on a starved slice.

**Phase A and Phase B fire this differently, and both matter.** In **Phase A** the sample is bounded by construction, so a raw survivor count under 500 means nothing and a hard flag there would cry wolf on every run. Report instead the **offer-fit drop rate** and the **projected survivor count across the wave's scope** ("offer fit removed 38% of the sample, projecting roughly N survivors across the wave's scope, under the 500 floor"; for the whole-TAM first wave the scope is the full universe). That projection is the more valuable warning, because it lands **before** the Phase B enrichment spend, while relaxing the criterion is still free. In **Phase B** the counts are real, so the hard sub-floor alarm above fires on the actual survivor count.

### Layer 1b: enrich the survivors only (the expensive beyond-source signals)

Run enrichment **only on `enrichment_tier = enriched` rows** (`good` + `maybe`); this is where the per-record/per-page money is, so gating it to good-fit is the saving. **Tool priority: the company-data provider first, then the discovery source's native enrichers, then the rest of the light stack (web crawl / web search / paid scraper / people-database company endpoints).**

> **Primary-provider-first, exhaust-then-gap-fill. HARD RULE (operator directive 2026-06-29).** For every `enrich` column the company-data provider *can* return, **run that provider across the WHOLE survivor set first, then route ONLY the cells it left blank** (plus the columns it has no field for at all) to the next tool. Never open a paid fallback on a column the primary provider covers until the primary has had its pass and you know which cells are actually still empty. The fallback tools fill *only the gaps*. This is the company-level twin of the contact-level rule already binding in `/email-waterfall` (the finder finds first, the waterfall enricher is residue-only), and its purpose is identical: never pay a second tool for data the cheap-first tool already returned. **Scope, honestly:** the saving is real but **column-scoped**. It only bites where the primary provider and a paid fallback *overlap*. Typically-covered `enrich` columns are `is_hiring_now` / hiring titles (`job_posting_*`), `has_public_pricing` / `has_demo_cta` / `has_contact_sales_cta`, `technologies_used`, web-traffic, and funding; web-crawl-only signals (proof/case-studies detail, news triggers, industry-idiosyncratic columns) have no provider field, so there is nothing to "fill first" and they go straight to their one cheapest-capable tool. Treat this as a routing discipline on the overlap columns, not new machinery. (The cheap-qualify-before-enrich gate still runs first: firmographics arrive free with discovery and feed the `fit_status` score, so you never pay per-record on a bad-fit company.) Claude pulls what the company-data provider and the discovery source's native enrichers return (source-native, see below). **By default (`seat_a`) Seat A then collects the beyond-source columns itself** (enrich-crawls, paid-scraper ads, org-depth, external web search; steps 5-7 below) via the fast crawl in this layer, going straight to step 8 (derive) when done. **Only under the operator's `seat_a_then_revcode` choice** are those beyond-source columns instead routed to the external enrichment platform via the **Layer 1c** copy-paste handoff (the operator runs them with their own integrations); on that path Claude resumes at step 8 once the external CSV returns. **For the beyond-source `enrich` columns (steps 5-7), pick the tool by the `/lead-list-tech-stack-research` Collection Routing Priority ladder (free public/official datasets -> web crawl (WebFetch) -> web search (WebSearch) -> a Claude Code sub-agent extraction) and use a paid scraper only where no lighter active tool returns the field. This holds whether Seat A collects them (`seat_a`) or the external platform does (`seat_a_then_revcode`).**

> **Run the Seat A enrichment crawl FAST (HARD RULE, enforce at run time).** The survivor crawl is the heaviest compute in the pipeline and it is **concurrency-bound, not per-site-bound** (a crawl returns in ~0.5s in any mode), so the tuned config below is the required default, not an optimization to remember. On every large enrich crawl use: the crawler's plain-HTTP request mode with **proxy off** first (escalate to a headless-browser mode only on a 0-page result), a page `limit` of 2, independent providers issued in parallel, and **~40 concurrent workers** (push toward the 429 knee, watching whichever provider throttles first). Measured ~9x over the naive smart-mode / limit-4 / serial / 16-worker default (~15 to ~133 rows/min, 0x429). **No AI model runs inside the crawl loop (no-AI-API rule, operator directive 2026-09-22):** the crawl writes page text to disk, and Claude Code sub-agents extract the fields afterwards in disjoint batches.
> **Runtime tripwire (this is the enforcement, not a note).** If the crawl is running below ~100 rows/min, STOP and fix the config before continuing: you almost certainly have the proxy on, a browser mode first instead of plain HTTP, `limit` above 2, or too few workers. A slow crawl is a misconfiguration, not the normal rate. Leaving the proxy enabled alone is an ~8-9x slowdown.
> **New enrich scripts MUST copy the proven pattern, never re-derive it from memory:** start from an existing enrich-crawl script in `scripts/` that already bakes in the ~40-worker concurrency, the hard fetch timeout, the http-to-browser escalation ladder, the credit floor, and resume-on-done, rather than writing a fresh crawl loop.
> **Kill any orphaned crawl process before relaunching** (a slept or relaunched job keeps appending to the same enrich journal file, wasting credits; resume-on-done makes the dupes harmless but kill it anyway). Full measured settings live in `/lead-list-tech-stack-research` section 7 (Fast-crawl settings).

A derived column with no recorded `derived_from` basis is a guess: reject it, do not write it.

the paid signal columns held `in_reserve` as "not needed, offer-led" and any signal trimmed for the ceiling (signals are trimmed before companies or contacts, never after); the exact keyword stack used on the pull, and whether `offer.icp_inclusion` and `offer.title_stack` were read from offer lock or derived here; per-provider spend (estimate + actual via `/api-cost-governance`); and any segment crawled only partially (with what was skipped and why). For every column, record its `fill_method`; for each **derived** column, record its `derived_from` basis and confirm every named input is present in `tam.csv`. ## Monthly Refresh

TAM data goes stale. Refresh on a cadence (the note's Phase 2 maintenance), cost-gated each time. **Refresh `enrichment_tier = enriched` rows only**: re-pulling `enrich` columns for `qualified_out` companies would reintroduce the exact spend the fit gate avoided. Re-scoring `qualified_out` rows that may now fit (ICP loosened, or the company changed) is a deliberate later-wave re-qualification, not part of the monthly refresh.

- **Monthly:** volatile signals (running ads, hiring roles/velocity, pricing changes, new case studies, new companies in the universe).
- **Quarterly:** stable firmographics (headcount, funding, location).

**Capture the delta, do not just overwrite.** The refresh already re-pulls the volatile signals; computing what *changed* since the prior build manufactures the `change_timing` columns for near-zero extra cost. On each refresh, diff the new pull against the stored row and set: `pricing_changed_90d` (pricing differs), `added_tech_90d` / `dropped_tech_90d` (`tech_stack` gained/lost an entry), `started_ads_90d` (a `running_*_ads` flag flipped on), `headcount_trend` and `hiring_velocity_change` (direction vs prior), `funding_stage_changed` (stage advanced), and recompute `funded_last_90d` / `days_since_funding` from `last_funding_date`. Keep the prior values needed for the diff (or a small per-row history) so the comparison is possible; a first build with no prior leaves these blank rather than guessing.

Stamp `last_refreshed` per row. After each monthly refresh of a scored TAM, invoke `/lead-scoring` to recalculate the strongest timing signal and the total score. Recalculate stable fit components only when the ICP, offer, segment mapping, or stable firmographics changed. A scheduled refresh routine may invoke this skill; it must run `/api-cost-governance` first and fail loud on an empty or errored refresh.

## Stop Gates

- **Primary company list = the route the Filter-First Discovery HARD RULE sets, not a free operator pick.** By default the filter route in the house order (operator directive 2026-10-06, see `standing-rulings.md` `discovery-flow`; `provider-routing.yaml` `layers.company_discovery`): resolve the enums, run the AI Ark company sample on the filters and the keyword stack (never a guessed provider industry-taxonomy value), mine the include and exclude keywords into the refined search, read GetLeads `count_contacts` on it, then export the whole company list in GetLeads, with AI Ark's export in parallel only if fast and never as a gap-fill rung. The lookalike route runs only for a group that meets both of its conditions (the offer needs it AND the TAM is small or hard to build by filters), with the operator's approval of the untested tool, and `run_state.discovery_route` records which route ran. **Reveal and lookup-by-person calls are never a discovery rung.** Every other tool (WebSearch, the web crawl, paid scrapers, vertical revenue databases, people-database company endpoints) is **extension/augmentation** layered on top (firmographics, crawl signals, ARR, org-depth, demand), never the primary spine. Exceptions: a genuinely local-SMB / maps-first universe is its own list-building motion, and a signal-first list (scraping a directory, job board or event as the source of truth) is the `/lead-source-strategy` Lead Source Plan Mode motion; neither is this firmographic TAM spine.
- **A named tool out of balance, down or switched off (`/tool-balance-guard`, operator decision 2026-09-28).** Stop that step and ask the operator to top up or fix it, then resume on the same tool. Never substitute another tool or the next rung; a skip needs the operator's say-so in chat, recorded with `list_waterfall.py plan --skip-provider <tool> --skip-reason "<what was seen>" --operator-approved-skip`.
- **Offer not locked, so the offer-fit gate cannot be evaluated.** Layer 1a asks whether a business can actually use, stock, deploy, or buy what the offer delivers, and that question is unanswerable with no offer on record. If no offer set is locked in `client-profile.yaml` (neither `offer.lead_magnet` nor any `offer.segments` entry), STOP and route back to the offer work (`/lead-magnet-brainstorm`, or `/offer-intelligence` first when no candidate set exists yet) before discovering or classifying anything. **Never silently fall back to ICP-only scoring.** That is precisely the failure this gate exists to prevent: the build looks normal, and it quietly spends Layer 1b enrichment money on companies the offer cannot serve. `offer.lead_magnet: direct_offer` IS a locked offer (the offer-first play carries a direct CTA instead of a separate magnet), so apply the gate question to the underlying service that CTA sells rather than treating the sentinel as a missing offer.
- **Offer-fit gate reporting is not optional.** The gate counts as run only once the per-segment and per-group survival ledger is reported, with the sub-floor alarm at the TOP of the report whenever a slice lands under the ≥500-company eligibility floor. A gate that silently starves a launch slice has failed, even when every single row it dropped was dropped correctly.
- **No enrich spend before the fit gate.** Do not collect any `gate_role = enrich` column until Layer 1a has scored `fit_status` across the TAM and the gate has been applied. Per-record enrichment (org-depth, ads, company-provider detail) on the whole un-gated universe is the exact waste this skill exists to prevent.
- **Never delete a gated-out company.** `qualified_out` rows stay in `tam.csv` with their `qualify` columns + `fit_reason` so a later wave or a loosened ICP can revive them; gating means "don't enrich," not "discard."
- **No per-contact spend here.** If a step would reveal or verify a person's email/phone, stop: that belongs to `/email-waterfall` on a live slice.
- **By default (`seat_a`) Seat A does discovery + fit + ALL enrichment; the external enrichment platform is the operator's optional `seat_a_then_revcode` choice.** Claude runs the Layer 1a fit decision itself (cheap native classify off the discovery source's returned text plus its free homepage extraction, via Claude Code sub-agents over disjoint batches; a crawl escalates only the ambiguous rows), pulls source-native enrichment from the company-data provider (first) and the discovery source's native enrichers, and, under the default `seat_a` path, collects the beyond-source columns (crawls, ad-library scrapes, org-depth, external web search) itself via the Layer 1b fast crawl. **Only when the operator picks `seat_a_then_revcode` at the GO gate** are those beyond-source columns routed to the external enrichment platform via the Layer 1c handoff instead; on that path, BLOCK for the returned CSV, never synthesize those columns yourself, and never start `/campaign-strategy` while a default-set column is still out (a conditional signal column still out never holds `full_enriched`; see Phase B).
- **Spend ceiling: trim signals first, never companies or contacts (Aaron process alignment, operator directive 2026-09-22; supersedes the old "raise the ceiling to cover full collection" default).** If the Layer-1 estimate meets or exceeds `run_state.spend_ceiling_usd` (the standing \$100 per client run unless the operator set another figure), cut the conditional signal columns first, lowest value per dollar first and `worth_a_fight` last, and name every cut in the build report; the budget goes to mapping companies, fit and contacts before any signal. If the default set alone (mapping, fit, the free fields, contacts) still meets or exceeds the ceiling, stop and ask, per the standing budget rule (unchanged).
- **Paid collection stays inside the ceiling and inside the offer-need test.** The full `collect_now` set (the default set plus the paid signals that passed the catalog's offer-need test) is collected up front; a paid signal the offer does not need stays `in_reserve` as "not needed, offer-led" until a live test asks for it. What still needs operator approval is (a) collecting an `in_reserve` column that was cut for the ceiling, or (b) any collection whose previewed cost exceeds `run_state.spend_ceiling_usd` after the signal trim.
- **A list workbench push that falls short is never silently accepted.** If a push lands fewer rows than its CSV holds, report the shortfall at the TOP of the build report and retry once, re-pushing only the rows that failed (never the whole CSV again, because a webhook push appends and a full re-push would duplicate the rows that already landed).
