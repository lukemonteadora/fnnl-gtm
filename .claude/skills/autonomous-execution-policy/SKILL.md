# Autonomous Execution Policy

**From the former description:** Every flow and setup skill defers to this. It covers how the standing spend budget (never asked) replaces per-purchase confirmations, the rule against re-asking recorded decisions, the ask policy (find the answer first, ask once up front, store every answer) with the four mid-run stops, the one named draft-upload exception and the rails autonomy never relaxes, the don't-idle-wait / interleave rule, the browser/UI-fallback HARD RULE (finish no-API steps yourself in the browser, hands-free, but under the exact same boundaries, never to authenticate, pay-by-card, accept OAuth/terms, or cross any stop or rail), and the parallelize-by-default HARD RULE (fan independent work out across sub-agents instead of running it serially, with a disjoint-inputs + disjoint-output-targets + post-merge dedup guard so no two agents produce duplicate output). Read it too whenever you are about to wait on an async process.

The operator wants this flow to run **hands-free with as little back-and-forth as possible** (operator directive). This policy is the single source of truth for *when to proceed vs stop*. Where any other skill's older "ask at every material fork" wording conflicts with this, **this policy wins** for runs where `run_state.execution_mode = auto_execute` (the new-client default since 2026-09-24, paired with `review_protocol: phase_checkpoints` so a run stops only at checkpoint A, closing Phase 2, and checkpoint B, closing Phase 4; Phases 1 and 3 auto-approve, section 0; Aaron flow, see aaron-flow.md section 2; `review_gates` is opt-in).

## Stack Resolution (read before any tool step)

This skill names **capability roles**, never specific vendors. Resolve every role to the
tool this workspace has actually chosen by reading:

```text
outbound/stack-contract.yaml
```

Roles this skill uses: sending platform, mailbox provider, email verifier, waterfall enricher. (Research is not a stack role: it runs on Claude Code itself, the `/deep-research` harness plus WebSearch and WebFetch, per the no-AI-API rule, operator directive 2026-09-22.)

**If a role this step needs is empty or missing in the contract, STOP and route to
`/stack-setup`.** Never substitute a guessed vendor, and never hardcode a tool name into
an artifact this skill writes.

## 0. Four phases, two human checkpoints: the default way a run stops (operator decisions 2026-09-24 and 2026-09-28; checkpoints A/B, Aaron flow, see aaron-flow.md section 2, operator decision 2026-10-05)

The operator runs a client in four phases, each in its own fresh thread ("Phase N for <client>"): `/phase-1-onboarding`, `/phase-2-research-offer`, `/phase-3-list` and `/phase-4-copy-launch`. The protocol (the tracker, the read set, the handoff files, the freeze) is `outbound/reference/phase-protocol.md`. A new client gets `execution_mode: auto_execute` plus `review_protocol: phase_checkpoints`:

- **Inside a phase, never stop for a minor call.** Every skill runs its `auto_execute` branch: take the recommended default, record it, keep going, and list it at the next checkpoint under "Calls I made" so the operator can reverse it. Find the answer first, ask only up front, and store every answer so it is never asked twice (the ask policy, `outbound/reference/phase-protocol.md` section 3; house answers in `outbound/reference/standing-rulings.md`, one client's in `profiles/<slug>/rulings.md`).
- **Stop for the operator only twice: checkpoint A (closes Phase 2, Research and Offer) and checkpoint B (closes Phase 4, Copy and Launch).** A checkpoint is a short plain-words summary plus one native prompt carrying every question the phase needs (at most four, recommended answer first; a second prompt only if more remain). Checkpoint A is the one go-ahead batch: it carries the GetLeads export OK the first time a client reaches it (section 4) and the PlusVibe placement-test OK when no ruling answers it yet, with its cost read first; after each is answered once it is a stored ruling. Checkpoint B is the launch review before the operator presses Start in the sending platform.
- **Phases 1 (Onboarding) and 3 (List) auto-approve** (standing ruling `checkpoints`). Each still writes its handoff file and calls `phase_state.py checkpoint` like any phase, then immediately `phase_state.py approve --answer "auto: Aaron flow, no checkpoint 1"` (or "no checkpoint 3" for Phase 3) so the tracker's own phase numbering is unchanged; neither phase waits on the operator. The one question kept in Phase 1 is the client-website exception (section 3d): asked as one line at the end of the phase, never a full checkpoint batch.
- **Checkpoints are recorded by the phase tracker.** `outbound/scripts/phase_state.py` writes `outbound/profiles/<slug>/phases/state.yaml`, which holds the phase state, and each phase writes a handoff file (`phases/phase-N-*.md`) that the next thread reads. `run_state.checkpoints` is retired: the `place` backfill reads it once to place a client that predates the tracker, and nothing writes it again.
- **A phase freezes once the operator approves it.** Later rule changes apply to phases not yet started. A frozen phase reopens (`phase_state.py reopen`) only for a broken rail, a change the operator marks as breaking, or new client facts that contradict it.
- **Aaron makes the offer and copy calls, in every mode** (operator decision 2026-09-28, `aaron-lane.md`). After the Research QA verdict, a fresh `/ask-aaron` sub-agent decides the offers and who each goes to (Phase 2); after `/campaign-strategy`, a second one decides which campaigns launch and the copy (Phase 3). His call is final below the operator. The owning skills record it word for word and run only the rails (truth, `/spam-word-checker` and the send format, compliance, suppression and verified-only emails, the budget and the operator's Start). A failed rail goes back to him for one fix round, then only that item is held for the next checkpoint.
- **Files are plain text, in every mode** (operator decision 2026-09-28). Everything a run generates is Markdown (for people) or CSV, YAML and JSON (for scripts) in the client's profile folder. No deck, DOCX, PDF, spreadsheet or Google Doc is built unless the operator asks for that format for that file (project `CLAUDE.md`, "Generated files are plain text").
- **A pending client approval holds only Start** (Offer Readiness, operator decision 2026-09-28, `offer-readiness.md`). An offer the client has not yet said yes to is built like any other (list, copy, paused draft); only its Start waits, with a 48-hour nudge drafted for the operator and never a send on silence. The client's yes or no is recorded only by `outbound/scripts/offer-readiness/offer_approval.py`, and a `no` or `vetoed` offer is never built.
- **Front-load the operator-only facts, after resolving what you can yourself (operator directive 2026-09-24).** Anything a later phase would otherwise stop for is settled by checkpoint A, since Phase 1 auto-approves (section 0). First the run resolves it from ground truth, as described under "Resolve it yourself first" in `/cold-email-kickoff`:
  - The speed-to-lead owner defaults to FNNL Agency.
  - The booking link comes from the context sweep.
  - The sending pool is read from PlusVibe.

  Only what survives the ask test is asked. The opt-out handling is never asked: it is always the FNNL house default for every client and geography, including Canada, the UK and Ireland (no opt-out line in the body, the one-click List-Unsubscribe header carries it, opt-outs by reply). When `client-profile.yaml` has no entry under `capability_boundary.legal_or_compliance_limits`, the skill records the house default there itself, citing "operator directive 2026-09-30, always house default"; a stricter requirement from the client's own counsel, already on record, is honored (`/campaign-copywriting`, Compliance, item 0a; standing ruling `opt-out`). Keep the process lean: never ask a question the build can proceed without.
- **Client asks never hold the flow.** They are batched into one `client-asks.md` message that the operator sends (Claude never sends it). Only the specific item that cannot happen without the answer waits.
- **An empty or `deferred` infrastructure or sending-platform slot never holds phases 1 to 3.** It stops only the step that uses that tool (CLAUDE.md section 1).
- **Only the four stops in section 3a stop mid-phase**, the moment they are hit, one at a time, while unblocked work continues. So does the one named exception FNNL keeps, the context sweep draft-upload stop in `/cold-email-kickoff` Step 6. Everything else is a hold on the one item it touches, a checkpoint question, or a note (the ask policy).

The phase skills own the four stops and record each one with `phase_state.py`, and `/continue-client` routes a resume to the right phase. `review_protocol: per_phase_gates` with a `review_gates_list` is honored exactly as written, `none` runs straight to paused drafts, and a profile with no `review_protocol` behaves as its `execution_mode` always did. An existing profile keeps its settings until the operator changes them.

## 1. Under `auto_execute`: proceed, don't ask

Under `execution_mode = auto_execute`:

- **Pick the strongest option, record it, proceed.** Offer, launch campaign, mailbox mix, billing period, sender persona, domain candidates, source workflow: choose the best per the skill's own rubric, write it to `run_state`/profile, and keep going. The one exception is the offer: lock the whole test set the Aaron offer call returns, as `/lead-magnet-brainstorm` records it (a primary plus ranked validation arms), send the first-wave offers together, placed by fit (equal cells on shared ground), and let `/campaign-strategy`'s flip criterion pick the winner in market, because Aaron tests three or four offers rather than picking one in advance (doctrine §5; operator directive 2026-09-22). Then the winner goes to the rest of the TAM immediately, with no client scale-review gate: `/offer-test-slate`'s scale review is a results report, and only an offer whose deliverable the client literally supplies stays capped at the client's confirmed capacity (Aaron process alignment, operator directive 2026-09-22; supersedes the scale review as a volume gate, 2026-09-22). Do not pause to have the operator pick.
- **The whole-TAM first wave is the default.** A new client's first wave is the whole qualified TAM at full volume, with the offer test inside it (`/cold-email-kickoff` First-Wave Default). A slice-first launch happens only on the operator's explicit request, never as an autonomous choice (Aaron process alignment, operator directive 2026-09-22).
- **The Research QA gate never pauses a run** (`/market-evidence` synthesize, `market-evidence-standard.md` section 7; added 2026-09-23). A DEEPEN verdict runs at most two targeted research loops, and after them the verdict is PASS with low-confidence labels, or HOLD. A HOLD proceeds to the Aaron offer call with every cluster labelled low confidence, the HOLD reasons flagged at the top of the report, and the missing evidence (usually call recordings) requested from the client and logged PENDING. Never a silent block, never a silent pass. Under `review_gates` the verdict is shown instead at Gate 2 (the offer-step review defined in `/cold-email-kickoff`), where the operator decides on a HOLD. Under `review_protocol: phase_checkpoints` research and the offer are one phase: the same loops run inside Phase 2 with no stop (operator decision 2026-09-28), the Aaron offer call follows, and the verdict and any HOLD reasons lead checkpoint A, which offers one more targeted pass only when a HOLD or a low-confidence cluster sits under the leading offer.
- **`/market-evidence` feedback runs without asking** (added 2026-09-23). `/cold-email-weekly-rhythm` runs it at each arm read and at least every two weeks while a wave is live, turning replies and call notes into evidence rows and a dated results review. It reads live campaigns and never edits them, never touches an arm's `status`, `read` or `flight`, and never moves the offer-validation flip.
- **Capacity is sized to the volume, never trimmed** (Aaron process alignment, operator directive 2026-09-22; supersedes the capacity trim at launch). The run files `run_state.capacity_request` (the daily sends that first-touch the whole TAM in about one Monday-to-Friday sending week), and the fleet `/mailbox-mix-strategy` sizes, or the pool group `/mailbox-pool-staging` assigns, is sized to it, inside the setup total the operator approves (section 2). If the fleet delivers less than `daily_sends_needed`, the wave still covers the whole TAM at the allocated rate and the runway stretches; report days to cover. Offers and TAM rows are never cut to fit (`/cold-email-kickoff` Steps 4 and 6).
- **Report, don't gate.** State what you chose and why in one line, then continue. The operator can correct in flight.
- **A low balance is a warning, never a question.** A key under its warning threshold warns and proceeds as long as it still covers the step; only a tool that is out of balance or down stops (section 3a, `/tool-balance-guard`).
- **Never re-ask a recorded decision.** If it's already in `standing-rulings.md`, the client's `rulings.md`, `run_state`, `client-profile.yaml`, `campaign-plan.md`, the profile, a saved memory, or the operator's latest message: use it silently. (Persona, mailbox mix, `billing = Monthly`, locked offer/campaign, domain list, etc.)

`execution_mode = review_gates` keeps the per-fork confirmations and is opt-in, set by a confirmed intake form or an explicit operator instruction. A new client gets `auto_execute` with `review_protocol: phase_checkpoints` (section 0; operator directive 2026-09-24, replacing the 2026-09-23 ruling that `review_gates` is the default). An existing profile keeps its mode until the operator changes it.

## 2. Spend: a standing budget, never asked

- **Every client run gets a standing budget of \$100 (operator directive 2026-09-22, which replaces the 2026-09-18 hold-at-\$0 default in `stack-contract.yaml`).** Onboarding, intake, kickoff and run start never ask about spend. `run_state.spend_ceiling_usd` is written as `100` for every client, and each new wave starts a fresh \$100. If the operator names a different figure for a client, record it (with the date and their reason) and use it silently from then on.
- **Auto-approve every paid data step whose running total stays within the budget**: enrichment, contact and verification credits, and list-workbench Actions. This holds under both `execution_mode` values, because it is a spend rule, not a strategy gate (`review_gates` still stops at its strategy forks, such as the TAM GO gate, where the whole universe is the default and a slice-first launch happens only on the operator's explicit request). Report each charge ("Spent $X of \$100") but do **not** stop to confirm.
- **Mailbox infrastructure is outside the budget.** Domains and mailbox capacity are bought only after the operator approves that setup's purchase total once (the kickoff infrastructure step asks for it). Then auto-approve every purchase whose running total stays inside the approved figure, report each ("Spent $X of $Y approved"), and never re-confirm per purchase. The \$100 data budget is never authority to buy infrastructure.
- **Only stop when a purchase would push a running total over its budget.** Then surface the overage and ask to raise it for this client.
- **Older profiles.** A `spend_ceiling_usd` of 0, null, or missing that was only the old ask-first default (no note beside it, or a note saying it is the workspace default) becomes `100` (the operator approved this switch for existing clients on 2026-09-22): rewrite it, log `UPDATED run_state.spend_ceiling_usd -> 100 (standing budget)`, and say so in one line of that run's report, as a notice rather than a question. A figure the operator set on purpose (it carries a note) stays, scoped as its note says, until they change it. The old AI research budget field (`research_budget_usd_per_provider`) is gone, so ignore it.
- **Track the running total in the client's activity log.** Each paid step appends one line, `NOTE spend: +$X on <step>, wave total $Y of \$100` (infrastructure purchases log against their approved setup total instead), so a resumed session can add up what the wave has already spent. A wave starts when a new launch wave is selected (kickoff Step 6, or `/continue-client` routing a new wave), and its total starts at \$0.
- **The list phase shows its spend up front, but still never asks for it inside the budget.** Checkpoint A (end of Phase 2, the stop before the list phase) reports the Phase 3 estimate (the contact enrichment tool plus the email verifier per contact) as a line of information. Inside the budget it auto-approves like any other paid step. An estimate that would cross the budget is the one spend item that checkpoint asks, so the list phase never stops mid-run to raise it.
- Still route spend through `/api-cost-governance` for the preview and the ledger; the budget is the approval, not each click.

## 3. What stops a run, and what never does (the ask policy, operator directive 2026-09-30)

The ask policy in `outbound/reference/phase-protocol.md` section 3 is the source of truth: find the answer first, ask only up front, once, in one batch at a checkpoint, decide the small calls and list them under "Calls I made", and never ask the same thing twice. House-wide answers live in `outbound/reference/standing-rulings.md` and one client's answers in `profiles/<slug>/rulings.md`. This section does not restate that policy. It lists the stops that remain, the rails autonomy never relaxes, the calls that are decided rather than asked, and where each old stop went.

### 3a. The four mid-run stops (only these, in every `execution_mode`), and FNNL's one named exception

When one is hit, stop that step at once, save progress, ask in chat now rather than at the next checkpoint, and keep other unblocked work going (section 5).

1. **A tool the step names is out of balance, down or switched off** (HARD RULE, operator decision 2026-09-28, `/tool-balance-guard`). Out of balance means credits, plan fair use, or GetLeads wallet cash for a paid scrape; down means a missing or rejected key, or an outage that outlasts two retries. Stop that step the moment it is seen, save progress, and ask for the top-up or fix in chat at once, not at the next checkpoint. Never route the step to another tool or the next waterfall rung instead, and never hand partial output on as complete: this overrides the 2026-06-19 exception that let the enricher open a down finder's rows as the finder. The only way through is the operator saying so in chat for that step of that run, recorded with `list_waterfall.py plan --skip-provider <tool> --skip-reason "<what was seen>" --operator-approved-skip`. A `429` rate limit is retried, not stopped, and Clay credits are never a fallback. Other unblocked work continues; the stopped step, and every later rung of it, waits. **The pre-phase check probes every key the phase will use** (`/tool-balance-guard`), so this stop should be raised before the phase starts, not halfway through it. A key under its warning threshold only warns and proceeds.
2. **Spend over the run's budget** (`run_state.spend_ceiling_usd`, the standing \$100 unless the operator set another figure), or an infrastructure purchase beyond the setup total the operator approved (asked once, section 2). Spend inside the budget is never asked (section 2).
3. **Aaron's offer or copy contradicts a client requirement, instruction or note** (`aaron-lane.md`, the client-fit check; standing ruling `aaron-auto`). The run stops and shows the operator the exact contradiction. Aaron's calls that contradict nothing are used as he wrote them, with no approval question.
4. **A required key is missing** (`/preflight-credentials` exit 1).

**The named fifth exception FNNL keeps: the context sweep draft-upload stop** (`/cold-email-kickoff` Step 6, `client-context-sweep.md` Gates). Immediately before the paused draft is uploaded, stop and ask, even under `auto_execute`, when the `context_sweep` block is missing, a core source is still `blocked` and not `waived_by_operator`, `unresolved_blocklist_names` is above zero, or a found blocklist is not yet in `suppression-list.csv`. It stays because it protects the send from a miss the sweep would have caught. The wording "reuse with judgment" (`phase-protocol.md` section 3) only decides which past answers carry over; it never removes this stop or any other.

### 3b. Rails autonomy never relaxes (they hold an item, never the run)

- **The agent never presses Start.** Uploads create PAUSED/DRAFT campaigns only; the operator launches. **HARD RULE: drafting is NOT warmup-gated (operator directive 2026-06-17):** the moment the copy sequence is approved / QA-passed and the verified list is ready (and `sending_platform` is locked), build the campaign **fully** in the sending platform: sequence with all variants, leads loaded, the correct sender accounts attached, settings (tracking, stop-on-reply, and the rest of the sending platform's pre-set defaults as resolved from the stack contract: client tag, schedule, and delivery toggles), and schedule, so the ONLY thing left for the operator is *review + press Start*. Never hold off building the draft because mailboxes are still warming. Warmup, placement tests, and Gates A/B/C/D gate the **live send**, not the draft build.
- **Pre-launch safety gates** (warmup ≥2 weeks, inbox-placement/auth, final QA, and reply readiness under Gate D, added by the Aaron process alignment, operator directive 2026-09-22). These BLOCK the **live send / Start** on fail, and so does an offer the client has not yet approved (Gate C, Offer Readiness, section 0). They are guardrails, not preferences. Never relax them for autonomy. They do **not** block building the PAUSED draft (see the drafting HARD RULE above): the draft is staged complete and ready while warmup runs, so launch is one click the day the senders mature.
- **Verified only.** No sendable copy or finalized campaign object for a slice before its VERIFIED-LIST GATE passes (`verified-list-gate.md`: a verified `leads.verified.csv` slice, a list-quality grade of B or better, a locked strategy). Unverified emails (`risky`, `unknown`, `invalid`, not verified) never ship and are never asked about (standing ruling `unverified-emails`); verified catch-alls follow the `catch-all` ruling automatically. A slice that fails the gate is held; the other slices go on.
- **Suppression.** Every blocklist found anywhere goes into `suppression-list.csv` at once, automatically, with company names resolved to domains; a name that cannot be resolved is listed at the next checkpoint (`client-context-sweep.md`). A do-not-contact list still owed holds only Start (standing ruling `dnc`). Suppression rows are never removed without the operator.
- **Entering financial credentials, adding a card, or enabling standing auto-recharge.** The operator owns payment. The agent MAY spend from an already-funded wallet or an already-saved payment method within the run's budget (or, for infrastructure, within the setup total the operator approved), but must never type card details or set up recurring billing config.
- **Locked choices stay locked.** The agent never changes the locked provider stack, the sending platform, or a source-of-truth artifact after it's locked. A step that would need such a change, or a role with an empty slot in the stack contract, holds only that step (route to `/stack-setup`), and the question goes to the next checkpoint.
- **Research routing & primary-pass enforcement (no-AI-API rule, operator directive 2026-09-22).** `run_state.research_routing` has exactly one value, **`claude_deep_research`** (the Claude native `/deep-research` fan-out harness, `anthropic-skills:deep-research`, run through the Skill tool): set it when unset, and treat a retired `third_party_ai` or `claude_native` value as `claude_deep_research`. Proceed on it; do NOT stop to ask. When the harness is unavailable or rate-limited, its declared fallback is a flat fan-out of 4 to 8 research sub-agents from the same brief, logged as `claude-subagent-fanout`; that is still Claude Code, never another provider. There is no third-party research engine and no research key: research runs only on Claude Code itself, so a missing key can never be a research stop, and gaps are filled by a second targeted `/deep-research` pass or WebSearch/WebFetch, never another AI provider. The Stage-1 primary research pass MUST be an **actual logged `/deep-research` run, or its declared fan-out when the harness fails** (the harness + the `api-balance-ledger.md` run-log line that `scripts/research/research_routing_check.mjs` reads + `ai_research_provider += claude-deep-research`, or `claude-subagent-fanout` when the fallback ran); finishing a research step with no logged deep-research primary is a **flagged violation**. Bulk crunching and classification run as Claude Code sub-agents fanned out per section 9 and `/personalization-subagent-pattern`. Full rule: `/ai-model-routing`.
- **Irreversible deletes and anything in the global safety rules** are never auto-done, on any channel (section 6).

### 3c. Calls I made: decided, never asked

These take the recommended default (or the stored ruling), are logged, and are listed under "Calls I made" at the next checkpoint so the operator can reverse any of them:
- Which of two near-identical titles, a borderline company, a count, a date, a setting.
- Launch settings inherited from a past campaign and every departure from them (sender-side values carry over, target-side ones are derived from the new campaign; standing ruling `launch-settings`).
- The start date (drafts are built paused, the schedule starts the next weekday; standing ruling `start-date`) and the sending-capacity figure (a note, never a trim; standing ruling `capacity`).
- Reusing an existing profile, segment merges, the Research QA verdict, the TAM GO gate inside the budget, and the launch set and copy exactly as Aaron wrote them.
- Which verified catch-alls ship and when (the Catch-All Timing rule), and which unverified emails stay out.
- The opt-out handling (always the house default, standing ruling `opt-out`).
- Any answer found by the find-it-first order (a ruling, the profile, the sweep), cited in one line.

### 3d. What used to stop a run, and where it went

| Old stop | Now |

| A failed 25-account list QA before Phase B spend (`/tam-build`) | The `qa-loops` ruling: one fix round. A second failure names the targeting question behind it; a stored ruling is applied and the slice reruns once, and with no ruling only that slice is held and the question goes to the next checkpoint. Never a third round. The held slice's Phase B spend waits; the rest of the wave goes on |
| A legal or compliance question with no ruling | The opt-out is always the `opt-out` ruling (house default, never asked). Any other legal risk is a hold on the touched item, noted at the next checkpoint |
| A client website no route can read | The one question kept in Phase 1 (`client-website-scrape.md`): asked as one line at the end of the phase, never a separate mid-phase stop or a full checkpoint batch (Aaron flow, see aaron-flow.md section 2.1) |
| A core sweep source that cannot be read | Asked once at checkpoint A, only when the find-it-first order has no answer, and the answer stored in the client's `rulings.md` (`sweep:<source>`) (Aaron flow, see aaron-flow.md section 2.1). If it is still blocked and not waived at Step 6, the named exception in 3a applies |

When one of the four stops in 3a (or the named exception) is hit, surface it crisply with the exact thing needed, and (per §5) go do other productive work rather than idling on the answer.

## 4. Bundle the unavoidable asks

When you genuinely must ask, **batch every needed decision into one interaction** with pre-filled recommended answers (native Interactive Inputs), per the ask policy (`phase-protocol.md` section 3, rule 2). Don't drip one question per step. One upfront batch >> five mid-run prompts. Under `phase_checkpoints` that one interaction is the checkpoint prompt at the end of the phase (section 0).

**GetLeads exports are confirmed once per client (operator, 2026-09-30).** The GetLeads export tool has its own confirmation step, and it is a paid step, so it is never treated as free. The operator gives it once, as one item in the client's checkpoint A prompt (end of Phase 2, the stop before the list phase opens), and it is written the same turn to the client's `rulings.md` as the `getleads-export` ruling (standing ruling `getleads-export`). That ruling covers every export in every later wave for that client. Read it before asking; never set `confirmed=true` without it. After it, nothing in the list phase stops to ask, except one of the four stops in section 3a.

## 5. Don't idle-wait: interleave (memory: `dont-idle-wait-interleave`)

When the flow hits a long async wait (mailbox provisioning → ACTIVE, 2-week warmup, DNS/WHOIS propagation, a scrape/enrichment job, a placement test), **do not sit in a tight polling loop.**

1. Start a background poll / wake-up for the waiting task.
2. **Move on to the next productive work** that isn't blocked: another client's setup (e.g. a different client's mailbox provisioning), skill/library updates, list building, copy, research, or the next independent step of this same run.
3. **Recheck the waiting task when the poll fires or when you next pause** on the interleaved work.

Never hold the session idle on a clock. Keep progress moving somewhere at all times.

## 6. Browser / UI fallback: finish hands-free, within the same boundaries (HARD RULE)

The operator wants the flow finished **for** them, not handed back with "do this last UI step yourself." So when a needed step has **no MCP/API path** (or the API genuinely can't do it), do **not** punt to the operator by default: **complete it yourself in the browser** (the harness browser pane or computer-use; never Claude in Chrome, per `outbound/reference/client-website-scrape.md`), the same way any provider dashboard step would be done by hand. This is a real expectation, not a nicety: a UI-only step is still your job.

Canonical examples of "no API, so use the browser hands-free":
- Running a **bound Google Apps Script** (e.g. the Cold Email Mailbox Tracker's `logInboxes_*` / `maintainCostsTab`): inject into Monaco, save, select the function, Run, read the execution log. (Done live on a prior client run 2026-06-16.)
- A **dashboard-only purchase from an already-funded wallet / already-saved payment method** within the approved budget (the run's standing budget for data, or the approved setup total for infrastructure), **on a dashboard the extension can actually drive**.
- A UI-only toggle, export, or setting with no API equivalent on an automatable dashboard.

**Tooling caveat: not every dashboard is automatable.** Some SPAs defeat browser automation. Some provider dashboards are known non-automatable surfaces: the page never reaches idle, so clicks, types, and screenshots hang (~45s) and fail. Where a UI is a known non-automatable surface, the browser fallback doesn't apply and the step stays operator-gated for that *tooling* reason, not because the rule exempts it. Try the browser, but don't loop on a surface already known to hang.

**The browser is just another execution channel: it is subject to the EXACT SAME boundaries as MCP/API. It is NOT a loophole that unlocks anything the rules forbid.** The stops and rails in §3 and the global explicit-permission list still bind on every channel. The browser fallback therefore must **never** be used to:
- enter passwords or **authenticate / sign in**; create accounts; enter card or other financial-credential details; enable standing auto-recharge;
- accept terms, consent/cookie banners, or grant **OAuth / SSO** permissions;
- submit a form containing personal data; click an **irreversible send/publish/confirm** that isn't already authorized;
- exceed the run's budget or an approved setup total, change the locked provider stack/source-of-truth, or relax a pre-launch safety gate.

**Practical gate (the decisive test):** the browser fallback only works on a dashboard the operator's session is **already logged into**. If the step would require *logging in*, that is the password/authentication boundary again → it's the operator's step, not a browser task: a tool that needs the operator's sign-in is down until they sign in (stop 1 in section 3a). Acknowledging an already-signed-in "you're signed in as X, OK?" context dialog is fine (it grants nothing new); a fresh login/consent screen is not.

**Calibration from a prior client run (so expectations are right):**
- The **tracker update** (bound Apps Script, no Sheets-API way to run `maintainCostsTab`) *was* exactly the in-scope case: done hands-free in the browser. ✅
- The **mailbox-capacity purchase** (funded wallet, no buy-capacity API) is the *shape* §6 targets, BUT that mailbox provider's dashboard was one of the non-automatable surfaces described above, so it stayed operator-gated for a **tooling** reason, not because the rule exempts it. On an automatable provider dashboard, the same buy IS a browser task. ⚠️ blocked by tooling, not by policy.
- **Linking one platform to another** (typing one platform's **password** into another platform's form) is *still* operator-only on every channel: the browser would not have changed that. Operator-only credential entry across platforms stays the operator's. ❌ stays operator-only.

When a step genuinely hits a boundary above, *then* surface it crisply with the exact action the operator must take, and per §5 go do other productive work meanwhile. But exhaust the browser-fallback path first; "there's no API for it" is not, by itself, a reason to stop.

## 7. Verify execution before you report it done - never assert (HARD RULE)

Running hands-free raises the stakes on truthful completion: the operator is not watching each step, so a false "done" can sit undetected for days (the canonical failure: an agent reported it had sent all the outreach, and only 25% had actually gone out). **Autonomy is never a license to report a step complete from your own claim that you acted.** Before you tell the operator anything is done, live, sent, uploaded, applied, removed, or built:

- **Verify against ground truth, not the action.** Query the system that holds the truth (the sending platform's actual sent count / campaign status / message history, a `GET` on the email accounts, the file on disk, a re-read) and compare to objective done-conditions. A `200` / exit-`0` means the request was accepted, not that the outcome is correct. Across a batch, check the count/coverage on the whole set - "most worked" is not "all worked".
- **Fail loud on any shortfall.** If part completed, or a condition could not be confirmed, surface it at the top of the report - never round a partial up to "done". A partial honestly reported is useful; a partial reported as complete is the costly failure this rule exists to prevent.

The full loop (falsifiable done-conditions → ground-truth evidence → worker-≠-judge check) lives in `/verify-execution`; run it before reporting completion of any high-stakes step in an autonomous run.

## 8. What "less interaction" does NOT mean

- It does **not** weaken the PAUSED-draft rule, the pre-launch gates, the spend ceiling, or any global safety rule.
- It does **not** mean guessing silently on a genuine fork with no sensible default: if there's no stored ruling, rubric or default and the choice is material and irreversible, hold that one item and ask it once in the next checkpoint batch (ask policy rule 2); the rest of the run goes on.
- It does **not** mean skipping the record step: autonomous choices must still be written to `run_state`/profile so the run stays resumable and auditable.
- It does **not** mean the browser fallback (§6) can cross a §3 stop or rail: a UI being the only path never authorizes a prohibited action.
- It does **not** mean parallelizing dependent or unsafe work: the §9 fan-out default never overrides an ordering dependency, a provider rate/spend limit, or any §3 stop or rail.

## 9. Parallelize by default: fan independent work out across sub-agents (HARD RULE)

Hands-free runs are long and the operator isn't watching, so wall-clock speed matters and there is no reason to do independent work one piece at a time. **When a step breaks into pieces that don't depend on each other, fan them out across parallel sub-agents (Claude Code Task tool, launched together in one message) instead of grinding through them serially.** This is the flow-level version of the workspace-level "Parallelize independent work" rule in this repo's `CLAUDE.md`. It used to be optional in these skills; it is now the default, and serial is the exception that needs a reason.

- **Mandatory trigger (checkable).** Fan out whenever the work decomposes into two or more independent sub-tasks: no shared mutable state, no ordering dependency, each chunk self-contained. In this flow that is the common case, not the rare one: TAM ICP-fit scoring, per-lead personalization (`/personalization-subagent-pattern`), per-company "why-now" research, multi-client weekly sweeps (`/cold-email-weekly-rhythm`), multi-artifact conformance audits (`/cold-email-flow-audit`), classifying or QA-ing a large list. Default these to fan-out.
- **Serial needs a one-line reason.** If the work clears the bar and you still run it serially, log why (a genuinely sequential dependency, a single tiny step, or a provider rate/spend limit that parallelism would breach). No stated reason means you should have fanned out. This is the enforcement tooth, in the same spirit as section 7's verify-before-done.
- **Hand each sub-agent an excerpt, not a whole skill.** Give it the rows or files, the rule text and the output format it needs. Loading whole skills into every agent multiplies each agent's start-up context, which draws on the same usage limit as the main session.
- **Right-size the split.** Cut the work into the smallest number of clean, independent chunks that genuinely run at once (useful Task-tool parallelism caps around 10 agents); the personalization pattern's 10-20 items per agent is a good default grain. Too big loses context, too small wastes orchestration.
- **Script-level concurrency already counts.** Where a builder script parallelizes correctly inside itself (the `email-waterfall` script's `--concurrency` pool against whatever tool fills the waterfall-enricher slot, the enrichment crawl's ~40 workers in `/tam-build`), that satisfies this rule for that step: don't also wrap it in agents, and respect that provider's limit. A pay-per-valid waterfall enricher throttles on its own side, so the speed lever there is the script's `--concurrency` setting, not more agents. Agent fan-out is for independent work that isn't already inside one concurrent script.
- **Spend-safe fan-out: the §2 ceiling still binds across all agents.** Each parallel agent sees only its own slice, not the running total, so N agents that spend concurrently (enrichment, verification, scraping) can collectively race past `run_state.spend_ceiling_usd` before any single total catches it. When the fanned-out work spends money, partition the budget too: give each agent a slice ceiling, or cap per-item spend so the worst case (every agent spends its max at once) still lands under the §2 ceiling. Spend over the ceiling is one of the four stops (§3a); fan-out never relaxes it.

**No duplicate outputs: the guard that makes fan-out safe (HARD RULE).** Parallel agents can't see each other, so without a guard they overlap or converge. All three layers are required:

1. **Disjoint inputs.** Partition so every item belongs to exactly one agent (by id, index range, or batch). Verify the slices cover the whole set with zero overlap before launch. No item processed twice.
2. **Disjoint output targets.** Each agent writes to its own file or key (`/tmp/<task>-<batch-id>.json`), never a shared file: concurrent writes to one file double-append or clobber (the same orphaned-double-write trap `/tam-build` and `/email-waterfall` warn about). Merge afterward by a stable id (`lead_id`).
3. **Post-merge uniqueness check.** After merging, catch convergent duplicates: different inputs that produced near-identical output (the "sub-agent wrote the same line 10 times" failure already flagged in `/personalization-subagent-pattern`). De-dupe by id and content, and re-run any converged agents with an explicit diversity instruction. Partitioning fixes overlap; only this step catches convergence.

The canonical fan-out plus merge plus dedup implementation is `/personalization-subagent-pattern`. Before reporting the step done, verify the merged set's count and coverage against the input (section 7). Fan-out makes a silent partial easy to miss.
